# 03 告警与通知

本任务依据 [产品约束](../brief.md)，采用 React + TypeScript 页面与 Go 模块。告警模块已进入实现并接入主干；以下保留设计约束，具体已交付接口、验证证据和首版边界见本文“当前实现与验收”。测试使用隔离数据库与本地接收器，没有配置用户的真实第三方账号。公共协议以主干 `docs/contracts.md` 为准。

## 交付目标与归属

在同一个 LightMoni 主服务里完成“创建告警组与通知目标 → 数据表绑定组 → 保存 SQL 规则 → 周期检查 → 触发/恢复 → 按组多渠道通知 → 查看失败原因”。所有规则、告警组与渠道全局共享，不增加项目、工作空间、大盘 ACL、复杂排班或另一个告警服务。用户管理与多个上报 Key 属于主干，本模块仅接入主干登录和授权接口。

| 归属 | 负责内容 |
| --- | --- |
| `web/src/features/alerts` | 告警组与目标管理、数据表绑定入口、已配置告警的表/规则总览、规则编辑/预览、事件、渠道表单、测试通知、静默与发送记录 |
| `internal/alerts` | 规则与告警组存储、来源表校验、表绑定的路由解析、调度、条件判断、状态机、事件与静默 |
| `internal/alerts/notify.go` | 渠道适配、消息渲染、持久化发送队列、限流、重试、发送记录与回执查询 |
| 主干 `internal/query` | 唯一的只读 SQL 执行器，统一宏/参数、时间范围、取消、资源上限、query frame 与 AST 实际表访问集合 |
| 主干表目录 | 稳定 `table_id`、业务/物理表映射、默认 `alert_group_id` 存储和配置入口、表存在性校验 |
| 主干 `internal/storage`、`internal/auth`、`internal/server` | SQLite 连接与迁移、凭证加密设施、登录保护、公共错误和路由注册 |

本模块提交自己的迁移定义，由主干集中注册；不修改公共初始化入口、独立创建另一套数据库连接或直接复制 ClickHouse 查询逻辑。模块间依赖通过 Go 接口和公共类型注入。首版调度与发送均在主服务进程中运行，SQLite 保存状态与 outbox，不需要 Redis、消息中间件或外部 cron。

## 告警组、表绑定与路由模型

告警组是用户必须可管理的配置对象，支持创建、重命名、启停、编辑目标、查看关联表和规则。渠道配置负责供应商类型、接口地址和凭证；组内目标负责“使用哪个渠道、发给谁”。规则不直接选择渠道作为主模型。

| 对象 | 最小结构与职责 |
| --- | --- |
| `AlertGroup` | `id`、名称、启用状态、配置 revision、`targets[]`；目标以 `(channel_id, recipient)` 唯一 |
| `AlertTarget` | 渠道配置引用 `channel_id` + 类型化 `recipient`，可附 @ 设置与显示名称；不把供应商秘密复制进组 |
| 表目录记录 | 稳定 `table_id`，最多一个默认 `alert_group_id`，为空表示未配置；一个组可绑定多张表 |
| `AlertRule` | 声明 `source_table_ids[]`、固定变量与 service 范围、SQL 与检查/判断配置；从来源表继承路由 |

接收目标的表单根据渠道类型展示：机器人使用该渠道绑定的群目标及可选 @ 人；SMTP 填具体邮箱；短信填具体手机号；pushplus 区分公众号/App、自身账号、供应商群组或好友绑定目标。保存时验证 recipient 类型与渠道匹配并做格式规范化；邮箱等不能直接混填到机器人目标里。机器人 Webhook 属于渠道秘密，组里引用已绑定群目标，不再次暴露或保存 URL。

- 单表规则从该表的默认告警组取得目标；跨表规则取得所有 `source_table_ids` 所绑定组的启用目标，按 `(channel_id, normalized_recipient)` 求并集去重。同一个目标被多张表/多个组引用只发送一次，记录所有贡献的 table/group ID 方便追溯。
- 来源表没有绑定组、组无目标、组禁用或目标渠道禁用都要明确显示。没有有效目标时规则可以继续评估并记录事件，通知状态为“未配置/无有效目标”，不能显示“已发送”或悄悄套用一个全局默认接收人。跨表规则部分表未配置时可通知其余有效目标，但总览、编辑和预览持续显示缺失来源。
- `source_table_ids` 是用户确认的数据依赖声明，不通过 SQL 文本正则或提示词猜测。保存与启用时由主干解析 SQL AST，解析 CTE/子查询/表别名后将实际读取的受管物理表映射为 table ID，与声明的集合逐一核对；不一致拒绝保存/启用并指出差异。表函数、无法解析的间接引用或非受管表不能绕过校验，需要明确支持和依赖解析后才开放。
- 修改 SQL 后重新校验来源声明。大盘/日志创建规则时带入候选来源表，但服务端仍对照 AST 验证。表目录重命名、删除、绑定修改都更新配置 revision，不能凭表名匹配旧目标。
- 每次事件在提交 outbox 的同一事务中解析并固定路由快照，记录来源表、表绑定/组/目标 revision 和规范化的最终目标。之后改变组或表绑定不将排队事件无声改投其他收件人；移除/禁用目标时取消对应未受理任务，未来事件使用新配置。
- 默认一个表绑定一个组，组内可以同时配置多个渠道与收件人；无需逐条规则重复填写通知目标。跨表取并集是首版唯一跨表路由，不额外增加任意规则级路由树。

## 规则与查询契约

规则至少包括：名称、启用状态、`source_table_ids`、SQL、固定的类型化变量值、声明的固定 service 范围或“全部 service”、检查间隔、回看窗口、查询结束延迟、数值字段、分组字段、比较运算符/阈值、持续异常时间、持续恢复时间、无数据/查询失败通知等待时间、严重程度、重复提醒间隔与来源跳转链接。告警组与最终通知目标通过来源表继承，由预览显示解析结果。

- 规则从大盘面板或保存的日志检索创建时复制查询与变量快照，之后独立保存；修改大盘或切换大盘下拉框不会改变运行中的规则。
- 只支持绑定值，不用字符串拼接替换变量。动态表名只能经过主干允许的表目录与标识符处理规则，不把任意变量文本当 SQL 标识符。
- 采用服务器 UTC 时间。一次评估固定 `evaluation_time`，窗口为 `[evaluation_time - delay - lookback, evaluation_time - delay)`；预览返回实际起止时间、绑定变量、结果与判断。复用主干的 `$__timeFilter(column)`、`$__timeInterval(column)` 宏和 ClickHouse 类型化参数，不定义另一套宏。告警聚合间隔由规则配置固定，不随图表宽度变化。
- 首版一条规则执行一条 SQL，不做任意查询表达式流水线。SQL 返回一个数值字段与零个或多个分组字段；每个完整分组组合只能返回一行，重复组合、非数值、NaN/Infinity、结果截断或超实例上限都判为查询结果错误，不偷偷求和或只评估前几行。
- 主干 `QueryFrame` 使用类型化列与二维 rows；Int64/UInt64/Decimal 保持字符串传输。阈值和比较由字段类型选择整数/十进制定点或浮点规则，不先全部转成 JS Number/Go float64。界面只格式化显示，实际判断在 Go 后端完成。
- 一条规则可按 `service`、主机或自定义属性产生多个告警实例。分组字段顺序、类型与规范化后的值生成稳定 fingerprint；不能把每次变化的测量值放入 fingerprint。
- SQL 不返回行或数值为 NULL 是无数据；`count() = 0` 是有效的零值，不能据此认定采集正常。主机失联、采集停更使用专门的“最近时间/窗口内样本数”规则模板。
- 分组结果中原来存在的实例消失，进入该实例的无数据处理；不能当成正常恢复。首版实例数量有可配置上限，持久化已知实例；关闭且长期无数据的实例可按明确的管理记录保留策略清理，不在一次查询缺失时删除。
- 预览是只读操作，不改变运行状态、不生成事件或通知；返回每个实例的值、阈值、建议状态以及查询错误。运行评估使用同一个判断函数。
- 告警查询有独立并发预算，调用主干统一的硬上限与超时；单条规则不得并发重入，上一轮未完成则跳过本轮并记录调度延迟，不能积压无限任务。

## 状态机与时间语义

内部建议拆成 `condition_state` 和 `evaluation_health`，避免“查询失败覆盖异常后误发恢复”。页面显示正常、待触发、触发、恢复中、无数据、查询失败，以及暂停/静默标记；“已恢复”是一条事件，完成后当前条件状态为正常。

| 条件状态 | 进入条件与行为 |
| --- | --- |
| 正常 `normal` | 有效结果不满足异常条件，没有打开的业务告警 |
| 待触发 `pending` | 第一次有效异常评估，开始异常计时；持续满足条件且覆盖配置时长后转触发，短暂异常回到正常 |
| 触发 `firing` | 创建一次业务告警 episode 与触发事件；持续异常维持同一个 episode，只按提醒配置产生后续通知 |
| 恢复中 `recovering` | 打开的业务告警首次得到有效正常结果，开始恢复计时；再次异常回到触发，持续正常完成后关闭 episode 并产生一次恢复事件 |

| 评估健康 | 行为 |
| --- | --- |
| 正常 `ok` | 继续上述条件状态机 |
| 无数据 `no_data` | 保留打开的业务 episode，停止推进异常/恢复计时；等待配置时长后可产生独立的无数据事件 |
| 查询失败 `error` | 超时、数据库断开、SQL/结果错误等；保留打开的业务 episode，停止推进异常/恢复计时；等待配置时长后可产生独立的查询失败事件 |

首版默认显示并在持续异常后通知无数据/查询失败，可由规则关闭这两类通知；不能将它们配置成“正常”来自动结束业务告警。评估恢复时关闭对应健康异常事件并产生健康恢复通知；若业务值仍异常，原业务 episode 继续触发，不能显示“业务已恢复”。

“持续”指有效评估之间无超出允许检查间隔的空档。检查被跳过、无数据、错误、进程停机都不能当作已验证的异常或正常时长。中断后重置尚未完成的 pending/recovering 计时，已经 firing 的 episode 保留。零等待时间也只在实际完成有效评估时触发。

保存每次评估的 `rule_revision`、时间窗、状态、值摘要、耗时与脱敏错误。修改 SQL、来源表声明、固定变量、分组或判断条件生成新 revision，废弃旧 revision 的 pending/recovering，关闭旧 episode 时标记“规则变更”，不发送正常恢复；仅修改显示名称、表绑定或组目标不重算测量结果，按路由 revision 处理后续通知。评估提交时校验 revision，避免运行中的旧查询覆盖新配置。

## 静默、通知与重启

1. 静默采用全局、告警组、规则或某个实例四种简单范围，设置结束时间即可。状态判断与事件记录继续进行，只抑制通知，记录 `suppressed` 原因。组静默抑制由该组贡献的目标；同一目标若还由未静默的组贡献则仍可发送，并记录路由来源。静默到期重新评估，仍异常则发送当前状态摘要，不能把静默期间全部历史事件重放。
2. 规则暂停不执行查询、不推进计时；恢复启用后检查当前窗口，按上面的中断规则处理。修改或删除渠道不能让仍在排队的任务发送到一个重新绑定的目标。
3. 状态更新、事件与 outbox 写入同一个 SQLite 事务。通知任务具有稳定 `event_id`，并按 `(event_id, channel_id, recipient, notification_kind)` 唯一约束去重；事件只发生一次，重试复用该任务。
4. 同一渠道可配置多份，组内可引用多个具体目标。规则求值后从表绑定的组解析目标并集，不再直接选渠道。可按最终渠道/接收目标短暂合并同一轮触发的实例，消息保留每个实例的状态；渠道之间独立执行，慢 SMTP 不阻塞机器人。
5. 通知任务保存脱敏摘要、模板版本、来源组与目标配置 revision，秘密通过受保护的配置读取。渠道密钥轮换可以显式让未发送任务用新凭证，组目标/接收人或表绑定改变时按路由快照保留原目的地或取消旧任务，不改投新目标；已接受的任务不重新发送。
6. 重试采用指数退避与抖动、最大尝试次数、任务有效期；识别网络失败、HTTP 429/5xx 与渠道业务码，尊重可用的 `Retry-After`。无效凭证、模板/签名错误等永久错误立即失败并提示修正，不无限重试。
7. 限流按渠道实例和供应商账号配额控制；多个 pushplus 配置共用 token 时也共用限流器。队列限额、积压、最老任务年龄和最终失败在界面与主服务健康指标展示。SQLite 写失败必须保持上次已提交状态，下一轮重试当前窗口，不能仅在内存中标记已通知。
8. 主服务重启后恢复状态、未发送任务和 worker lease。只评估当前窗口，不逐个补跑停机期间的检查点；已打开的 episode 保留，尚未完成的连续时间重新验证。到期任务标记 `expired`，不能突然发送一批过时的故障通知。
9. 同一 episode、同一渠道保持触发与恢复顺序。恢复时如果触发尚未发出，可合并成“故障已恢复”摘要，取消未发出的过时触发提醒；触发已被供应商接受则正常发送恢复。具体合并策略需主干统一冻结。
10. 内部事务去重不能承诺外部通知恰好一次。供应商接受后响应丢失、进程在记录接受结果前崩溃，都可能导致重复。支持供应商幂等时传稳定 ID；不支持且结果不确定时标记 `unknown`，优先查询回执。短信默认不盲目自动重发未知结果，避免重复收费；人工重试显式说明可能重复。

## 渠道范围与成功判定

适配器统一提供配置校验、渲染、发送、业务响应解析，以及可选的结果查询。返回 `retryable`、`retry_after`、`provider_message_id` 和状态；通知记录至少区分排队、发送中、供应商已受理、渠道确认成功、失败、结果未知、静默、过期。即使渠道返回“成功”，也不推断用户已经看到或读到消息。

| 渠道 | 首版配置与前置条件 | 成功、限制与边界 |
| --- | --- | --- |
| 飞书群机器人 | 渠道中设置 Webhook、签名密钥并引用群里创建的机器人；组目标选择该群与 @ 用户 | 内置消息模板和签名；同时解析 HTTP 与业务响应；限流通过适配器配置，不能复用钉钉签名算法 |
| 钉钉群机器人 | 渠道中设置 Webhook、加签 secret 或与机器人一致的安全设置；组目标选择群与 @ 手机号/用户 | 识别签名、关键词和 IP 限制错误；响应接受不代表成员已读 |
| 企业微信群机器人 | 渠道中设置群机器人 Webhook；组目标选择群与支持的 @ 标识 | 解析业务错误、内容大小与限流；群机器人 URL 视作秘密，不需要自建企业应用才能使用该适配器 |
| 微信公众号推送 | 首选 pushplus：渠道中设置用户 token；组目标选择自身、群组或好友绑定目标；用户完成供应商要求的账户与接收绑定 | 请求受理后保存流水号并查询最终结果；不要求每个 LightMoni 用户注册自己的公众号 |
| 手机移动推送 | 同一个 pushplus 适配器使用 `app` 渠道，组中配置具体绑定目标；安装、登录客户端并打开通知权限 | App 和公众号分别选择，不能把 `wechat` 当 App 通知；另可后续添加 Bark，首版不开发 LightMoni 手机 App |
| SMTP 邮箱 | 渠道中设置 SMTP host/port、TLS 模式、账号/授权密码和发件人；组目标填写收件邮箱 | 支持 TLS/STARTTLS；SMTP 接受只标记邮件服务器已受理，未接退信/DSN 时不标为邮箱已送达；按收件人记录拒收/失败 |
| 手机短信 | 首个实现选择阿里云短信：渠道中设置最小权限 API 凭证、已审核签名/模板与变量映射；组目标填写手机号 | 解析业务 Code/BizId，并查询最终发送状态；账号余额、频控与供应商模板要求需用户自行满足；短信超时不能直接重复调用 |
| 通用 Webhook | URL、请求头、JSON 模板、可选自定义签名、接收方约定的响应匹配条件 | 默认 2xx 仅表示接收方接受；传稳定事件 ID 方便接收方去重；可连用户内网服务，但使用明确配置和超时，不允许模板触发任意本地代码 |

消息统一包含：测试/触发/恢复/无数据/查询失败类型、规则名、service/主机/维度、值与阈值、采集窗口、触发/恢复时间、故障时长、LightMoni 详情链接。短信按已审核模板映射有限字段；机器人按格式限制截断并附链接，不把整批日志或 SDK 私有 Key 填入通知。

秘密不返回原文给前端，不写普通日志或发送记录；凭证加密、应用主密钥和备份恢复由主干提供。通知跳转 URL 取可信的主服务外部地址配置，不直接使用请求 Host 拼接。供应商回调如果缺少可验证签名，首版使用服务端结果查询，不能让匿名回调直接改成“已送达”。

### 已核对的官方依据

- pushplus 明确区分“请求受理”与异步发送结果，可凭流水号查询或接收回调；首版建议使用结果查询，支持无公网回调地址的部署。[消息接口](https://www.pushplus.plus/doc/guide/api.html)
- pushplus 当前有实名、频率、日额度和重复内容限制，免费与会员额度不同；配置表单给出官方链接，worker 不将配额数值当永久协议常量。[接口限制](https://www.pushplus.plus/doc/help/limit.html)
- 自有公众号是可选接入；pushplus 自有公众号绑定要求已认证服务号与对应模板配置。移动推送需 `app` 渠道及客户端通知权限。[自有公众号](https://www.pushplus.plus/doc/extend/mp.html)、[App 渠道](https://www.pushplus.plus/doc/channel/app.html)
- 阿里云 SendSms 要求审核通过的签名与模板，返回 `OK`/BizId 后仍需查询发送状态；官方说明短信 API 不支持幂等，超时要结合回执判断重试。[SendSms](https://help.aliyun.com/zh/sms/developer-reference/api-dysmsapi-2017-05-25-sendsms)
- SMTP 服务器接受 DATA 后负责后续投递，无法据此证明接收者阅读；首版状态用“服务器已受理”。[SMTP RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html#section-6.1)
- 机器人实现应分别依据供应商文档冻结签名算法、请求/响应 fixture 与限流映射。[飞书自定义机器人](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)、[钉钉机器人安全设置](https://open.dingtalk.com/document/robots/customize-robot-security-settings)、[企业微信群机器人](https://developer.work.weixin.qq.com/document/path/91770)。本次机器人动态文档未被读取工具完整展开，因此这里不写死未经确认的频率数值；实现时需要继续核对官方正文并记录所用版本，不使用其他供应商的签名或错误码替代。

## 依赖接口与页面

以下是语义清单；公共 API 统一使用 `/api/v1`，路由由主干冻结后生成 TS/Go 类型和模拟响应：

| 依赖/拟 API | 契约 |
| --- | --- |
| 主干 `QueryExecutor.Execute(ctx, request)` | SQL、类型化变量、绝对时间窗、固定聚合间隔、来源 `alert`；返回完整 frame、统计与可分类错误 |
| 主干 SQL 分析与表目录接口 | 实际表访问集合 → 稳定 table ID 集合，与 `source_table_ids` 核对；批量读表绑定与 revision，禁止未解析引用绕过 |
| `/api/v1/alerts/groups` 及 `/:id` CRUD/启停 | 组内渠道引用与类型化接收目标、关联表/规则、revision；被表引用的组不能直接删除，先明确解除绑定 |
| 主干 `PUT /api/v1/catalog/tables/:id` 的告警绑定配置 | 读写默认 `alert_group_id`，由主干拥有目录记录，调用告警模块验证组；返回当前绑定与缺失提示 |
| `/api/v1/alerts/tables` | 所有已配置告警的数据表总览，返回绑定组、关联规则、当前状态和路由完整性；支持告警组、table、service、启用状态筛选 |
| `/api/v1/alerts/rules` 及 `/:id` CRUD/启停 | 持久化来源声明与 rule revision；列表按组、table、service、启用状态筛选；不接收当前大盘临时变量作为运行参数 |
| `POST /api/v1/alerts/preview` | 草稿 SQL、来源声明与绑定值 → AST 校验、实例评估、继承组/最终目标和缺失配置；无状态和通知副作用 |
| `/api/v1/alerts/instances`、`/api/v1/alerts/evaluations`、`/api/v1/alerts/events` 分页查询 | 当前条件状态、健康、episode、值、最后成功评估、错误、组/来源表与静默原因；支持上述筛选和相互跳转 |
| `/api/v1/alerts/silences` 创建/撤销 | 范围、结束时间、原因；只有简单的时限，不做值班轮换 |
| `/api/v1/notify/channels` CRUD、`POST /api/v1/notify/channels/:id/test`、组目标测试 | 类型化表单、脱敏配置、具体测试 recipient 与任务 ID；测试遵守真实限流且显式标为测试 |
| `/api/v1/notify/deliveries` 与重试动作 | 分来源组/表/规则/渠道/接收人结果、尝试次数、供应商流水号；未知结果重试有单独的明确动作 |
| 主干存储/配置接口 | 事务、迁移注册、秘密加解密、服务器外部 URL、时钟与可取消的启动/停止钩子 |

前端页面分为告警表总览、规则列表/编辑、告警组/目标管理、告警事件、通知渠道、发送记录。总览涵盖“绑定了告警组”或“存在关联规则”的所有表，明确区分仅绑定但无规则、规则已启用、规则已暂停、来源无有效组等状态；跨表规则可以在每张相关表中展示，但通过 rule ID 识别同一规则。可按告警组、表、service、启用状态组合筛选，从表查看规则，从规则/组查看事件和具体发送记录；service 筛选依靠明确声明的固定变量范围与已观测实例，未知范围标注未声明，不能假装完整推断任意 SQL。

规则编辑按“来源表与查询/固定变量 → 检查窗口 → 判断条件 → 继承的告警组与通知目标”组织。保留 SQL 编辑、执行预览、真实结果表、趋势和分组实例判断，不以固定卡片替代 Grafana/Kibana 已约定的核心查询与排查交互。组编辑可以添加多种渠道目标并分别测试；数据表配置提供组绑定入口及反向的“查看该组所有表”。状态页面同时显示“最后一次有数据的时间”和“最后一次执行时间”，防止把检查成功误读成采集正常。

界面遵循主干统一的 oil-ui 设计说明与共享组件：使用 React 自定义 `Select`/`Combobox`/`Modal`/`Input`，禁止原生 `<select>` 和 `window.alert`/`window.confirm`/`window.prompt`；删除、解绑与未知结果重试用共享 Modal，字段错误内联显示。搜索、多选接收目标、键盘导航、焦点管理、空状态和错误反馈使用统一组件契约。本模块不引入独立 UI 库或复制一套设计 token；共享组件未准备好时先与主干对齐接口并基于 mock 开发，不偷偷退回原生交互。

## 开发顺序与并行方式

1. **契约先行**：与主干冻结 query request/frame、AST 实际表访问集合、table ID/默认组绑定、类型化 recipient、时间窗、公共错误、SQLite 事务和生命周期；提供组、已配置告警表、规则、状态与发送记录的模拟响应。共享自定义控件按 oil-ui 设计说明就绪后，页面可在 mock 上并行实现。
2. **状态与路由闭环**：完成告警组/目标 CRUD、表绑定集成、来源声明验证、配置总览和筛选；再完成规则 CRUD、只读预览、单进程有界调度、分组实例、状态机与 SQLite 事件/outbox；用本地 Webhook 接收器验证单表继承、跨表去重及触发/恢复。
3. **发送闭环**：实现队列恢复、限流、错误分类、幂等键、顺序、静默和记录；先完成 Webhook、SMTP、飞书/钉钉/企微适配。
4. **异步与付费渠道**：接入 pushplus 公众号/App 及结果查询、阿里云短信与回执查询；渠道模板和测试按钮完整可用。真实账号联调只在获得测试目标授权后执行，不向现有生产群发测试。
5. **联动与故障验证**：接大盘/保存检索的规则草稿入口；用 Docker ClickHouse、真实 Agent/SDK、主服务和本地 SMTP/Webhook 接收器完成整个链路，再完成真实进程重启、断网、数据库故障验收；主干提供安装后预置规则模板。供应商联调逐渠道登记实际凭证与授权测试目标的可用性。

模块只在自己的目录中实现，共享 HTTP 客户端、SQL 编辑器、时间控件和类型由主干或约定的公共组件提供。首次集成从 Agent 主机指标的“高 CPU”和“失联”规则开始，再覆盖日志错误数量、自定义维度计数和 HTTP 拨测。

## 验收与证据

使用隔离 SQLite、Docker ClickHouse 的隔离数据库和本地 HTTP/SMTP 接收器，不操作用户历史数据。最终必须真实运行“SDK/Agent → 主服务 → ClickHouse → SQL 求值 → 表绑定告警组 → 通知 → 事件/发送记录页面”，不能仅靠静态页面或模拟接口验收。以下项目以实现后的日志、数据库记录、抓取的请求、收件记录或界面截图作为证据，方案本身不代表已通过：

- 创建含机器人、邮箱、手机号、公众号/App 目标的组，绑定表并建立规则；总览能列出所有有组绑定或关联规则的表和规则，组合筛选组/table/service/启用状态后能查看对应事件与发送记录。
- 单表继承正确；跨表关联两个组且重叠目标时只发一次；来源表未绑定、组无目标、渠道禁用时明确展示；原 SQL 声明漏表/多表、CTE/子查询隐含访问、不可解析表函数都不能绕过 AST 验证。
- 多 service/维度返回多实例；短暂尖峰进入 pending 后清除，持续异常只触发一个 episode，恢复计时满足后只产生一次恢复；高基数或截断结果报错而非部分评估。
- ClickHouse 停止、SQL 超时、空结果、NULL、分组消失分别正确显示；触发中的告警不能因失败或无数据变成已恢复。`count() = 0` 与真正无数据的模板行为有明确区别。
- 杀死主服务后重启：分别在提交事件前、提交 outbox 后、供应商接受但确认未写入时注入故障；SQLite 已提交任务恢复，内部事件不重复，外部未知结果明确展示，不宣称恰好一次。
- 断开通知网络并恢复：队列有界，退避、429/业务限流和永久错误行为正确；一个渠道失败不阻塞其他渠道；过期触发不在恢复之后发送。
- 本地模拟 HTTP 200 + 业务失败、202 受理后结果失败、SMTP 收件人拒绝、供应商响应丢失；页面不能显示“已送达”。pushplus 查询结果和短信回执可以更新受理状态，伪造回调不能改状态。
- 静默、暂停、规则编辑、表绑定/组目标变更、组与渠道删除和重启组合验证：没有旧 revision 覆盖，没有历史通知洪峰，没有发往后来修改的接收人；表仍引用的组不能无声删除。
- 验证多个渠道配置共用供应商 token 时共享额度控制；消息模板截断、@、敏感字段脱敏、测试通知和查询预览正确。短信未知结果不会自动重复付费发送。
- 经授权的测试账号覆盖每种渠道至少一次触发与恢复，并保存供应商业务响应；没有真实账号的渠道仅标记“本地契约测试通过”，不能写“真实发送通过”。
- 交付逐渠道验收矩阵，区分 Docker/本地真实链路、模拟供应商业务回包、真实供应商受理/最终回执、缺少凭证未验收；准确列出飞书/钉钉/企微、公众号、移动推送、SMTP、短信、Webhook 哪些尚未完成真实验收。
- 浏览器实际操作验证告警组与多目标编辑、表绑定、筛选、SQL 预览和事件/记录跳转，确认使用统一自定义控件与 Modal；不得将主要交互降级为原生 select、浏览器弹窗或静态演示。

## 当前实现与验收（2026-10-10）

已交付 `internal/alerts/{types,store,api,evaluate,notify}.go`、`alerts_test.go`，以及 `web/src/features/alerts/AlertsPage.tsx` 和共享设计方向下的样式。主干通过 `New(shared.Dependencies)`、`Register(mux)`、`Run(ctx)` 接入同一个 Go 进程；表绑定仍由主干目录 API 管理，准确使用 `alert_groups(id, name, body)`。没有单独通知服务或外部队列。

当前包含告警组/类型化目标、渠道配置、数据表继承与跨表去重、来源 AST 对照、规则 CRUD 和只读预览、固定参数与滚动 UTC 窗口、多维实例、精确大整数/十进制阈值、pending/firing/recovering/正常状态、独立 no_data/error 健康、规则静默、提醒、事件、持久 outbox、重试/限流/回执和发送记录。页面提供告警数据表、规则、告警组、事件与发送记录四个视图，支持组/table/service/启用状态筛选和规则精确历史跳转。日志与大盘的 `/alerts?draft=<JSON>` 草稿保留 SQL、参数、来源表，并把原 range 的跨度作为回看窗口；保存/预览仍复验 SQL AST。

组、渠道和规则返回 `revision`，更新需要带上读取到的 revision，冲突返回 HTTP 409。存量 JSON 没有该字段时视为 revision 0，无需更改已有表列。只改规则名称保留业务 episode；暂停保留打开的 episode 并重置未完成计时；更改测量条件重置实例、取消未发送旧任务。事件记录规则 revision 与实际查询窗口。渠道目的地址/账号改动取消未受理旧队列，不把历史任务改投新地址。

### 可联调 API 与字段

以下路径均带 `/api/v1`。列表当前返回数组，事件和发送记录最多返回最近 1,000 条。

| API | 当前请求/返回 |
| --- | --- |
| `GET/POST /alerts/groups`、`PUT/DELETE /alerts/groups/:id` | `{name,enabled,revision,targets:[{channel_id,recipient:{kind,value,mentions?}}]}`；返回含 id/revision 的组；被表绑定的组拒绝删除 |
| `GET/POST /notify/channels`、`PUT/DELETE /notify/channels/:id` | `{name,type,enabled,revision,config:{...}}`；配置写操作由主干管理员权限保护；秘密加密保存，GET 不返回原值，编辑留空保留秘密 |
| `PUT /catalog/tables/:id` | 主干拥有，`{alert_group_id:"组ID"}`；传空字符串解除绑定 |
| `GET/POST /alerts/rules`、`PUT/DELETE /alerts/rules/:id` | Rule 包括 sql/source_table_ids/params/services/value_field/label_fields/operator/threshold，以及 interval/window/delay/for/recovery/repeat/health_for 的 `_seconds` 字段，notify_health/severity/enabled/revision |
| `POST /alerts/preview` | 未保存 Rule → `{range,result,states,routes,warnings}`；不创建事件/通知 |
| `GET /alerts/tables`、`/alerts/instances`、`/alerts/events` | `group_id`、`table_id`、`service`、`enabled` 筛选；实例/事件另支持 `rule_id` |
| `POST /alerts/rules/:id/silence` | `{until:"UTC RFC3339"}`；空字符串撤销；静默继续评估，旧 queued/retry 标为 suppressed，到期只发当前摘要 |
| `POST /notify/channels/:id/test` | `{recipient:{kind,value,mentions?}}` → 实际入队测试任务；同样遵守限流与发送记录 |
| `GET /notify/deliveries` | 支持 group/table/service/enabled/rule/status 筛选；受理与确认成功分开 |
| `POST /notify/deliveries/:id/retry` | 失败/过期可重试；unknown 必须 `{confirm_possible_duplicate:true}`，不会自动盲重试 |

`operator` 为 `gt/gte/lt/lte/eq/ne`，threshold 是字符串。`services` 是列表筛选声明，不会自动重写 SQL；实际 service 条件必须写入 SQL 并使用 params 类型绑定。`recipient.kind` 为机器人/Webhook 的 `channel`（value 为 `bound`）、SMTP 的 `email`、短信的 `phone`、pushplus 的 `self/topic/friend`。重复目标按实际接收地址去重，@ 设置取并集。

渠道 `config` 字段：

| type | 必要字段与可选字段 |
| --- | --- |
| `webhook` | `url`；可选 `secret`（原始 JSON body 的 HMAC-SHA256，`X-LightMoni-Signature: sha256=...`）、`headers`（JSON 字符串）；发送稳定 event_id/notification_id |
| `feishu`、`dingtalk` | `url`，可选机器人安全设置对应的 `secret`；分别实现各自签名，不能互换 |
| `wecom` | `url`；目标可带 @ 用户列表 |
| `pushplus` | `token`、`push_channel: wechat/app`；可选 `access_key` 用于服务端最终结果查询；没有 access_key 保留受理状态 |
| `smtp` | `host`、`from`、`tls: starttls/tls/none`；可选 `port`（默认 587）、`username`、`password` |
| `aliyun_sms` | `access_key_id`、`access_key_secret`、`sign_name`、`template_code`；可选 `template_params` JSON 字符串，支持 `{{rule}}/{{status}}/{{value}}` |

各渠道还可配置 `rate_per_minute`；worker 使用保守默认值，供应商实际额度仍以账号配置为准。供应商账号 key 共享限流；pushplus 900 账号限制会持久暂停该账号，修正并保存渠道后才能恢复尝试，遵守官方[返回码说明](https://www.pushplus.plus/doc/guide/code.html)。为本地协议测试提供可选 endpoint/receipt_endpoint 注入；正常配置使用官方默认地址。

### 大盘告警窗口与无数据策略（2026-10-11）

图表告警现在直接配置回看窗口和窗口结束延迟，并显示相对查询区间。回看 600 秒、延迟 120 秒对应 `[now-12min, now-2min)`；查询继续使用公共时间宏，配置不会绑定到大盘当前显示的绝对时间。

取值支持最新有效点、平均值、最大值、最小值、总和、有效点数。聚合跳过 NULL；窗口没有有效点时返回 NULL，由评估器统一处理，图表显示补零不改变告警输入。最新点按时间字段排序，点数是查询返回的有效图表点数。[ClickHouse OrNull 文档](https://clickhouse.com/docs/reference/functions/aggregate-functions/combinators#-ornull)说明了空输入返回 NULL 的语义。

规则新增可选 `no_data_policy` 与 `no_data_value`，沿用 JSON 存储，无需数据库迁移：

| 策略 | 行为 |
| --- | --- |
| 未设置 / `keep_state` | 保留旧行为：跳过阈值计算，保留已触发 episode，中断未完成的持续异常/恢复计时 |
| `zero` | 用 0 与阈值比较 |
| `value` | 用配置的有限数值与阈值比较；字符串保留大整数和十进制精度 |
| `alerting` | 将无数据视为异常，遵循持续异常时间 |
| `normal` | 将无数据视为正常，遵循持续恢复时间 |

策略覆盖空结果、NULL 和已知曲线消失；查询失败、超时、截断仍按查询健康错误处理。替代值不会推进最后一次真实数据时间，通知会注明窗口无数据及处理方式。单独的“没有打点”触发条件继续依据真实有效点数，不受替代值影响。告警中心也可编辑同一策略。

验证入口：`go test -race ./internal/alerts ./internal/dashboards`、前端 `npm run typecheck`、`node --test src/features/dashboards/panel-alerts.test.mjs`，以及 `node src/features/dashboards/verify-panel-alert-window.mjs`。浏览器脚本使用可通过环境变量覆盖的本地前后端和本地通知接收器，覆盖六种取值、五种无数据策略、真实查询范围、失败保存、刷新回读和 390px 布局；截图与报告存放在 `docs/evidence/panel-alert-window/`。
