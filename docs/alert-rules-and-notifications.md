# 告警与通知规则对齐（2026-10-16）

告警判定与通知分成两层：规则决定是否产生告警，告警组决定已经产生的告警何时、以什么方式联系值班人。本文记录当前实现，供应商与回执细节见[通知渠道](notification-channels.md)，排班与接手细节见[告警响应](alert-response.md)。

## 规则层：先判定，再产生告警

同一规则以分组字段生成的同一组标签识别一个指标实例。不同规则、不同实例分别计数，不能相互累加。

| 设置 | 当前行为 |
| --- | --- |
| 检查间隔 | 每隔指定秒数执行一次规则，默认60秒 |
| 回看窗口 / 窗口结束延迟 | 例如回看300秒、延迟60秒，查询 `[now-360秒, now-60秒)`；每次比较窗口查询的结果 |
| 条件 | 大于、大于等于、小于、小于等于、等于、不等于、没有打点；图表可取最新有效点、均值、最大、最小、总和、有效点数 |
| 连续异常检测次数 `for_count` | 连续N次检测结果异常才触发，默认1次，范围1～1000；正常、查询失败、默认无数据处理或超过两倍检查间隔的检测中断会重新累计 |
| 持续异常 `for_seconds` | 持续指定时长再触发，0为关闭时间门槛；普通新规则默认60秒，图表新规则默认0秒 |
| 次数与时间同时配置 | 两个门槛都满足才触发，例如N=3、持续60秒、每10秒检测，第三次异常时尚未满足60秒，需要继续等待 |
| 未达到触发门槛 | 当前实例显示待触发，不生成正式告警事件，也不发送通知；单次突刺可以在这里过滤 |
| 已触发且持续异常 | 沿用同一持续异常事件，不因每次检测而生成新的责任或重复接手 |
| 持续恢复 `recovery_seconds` | 正常持续指定时间后记录恢复，0表示检测正常即恢复；恢复前仍保留原事件 |
| 无数据 | 默认保留已触发状态、中断待触发计数；也可配置按0、指定值、视为异常或视为正常，后四种按配置后的结果参与判定 |
| 查询失败、超时或结果不完整 | 不当作正常、不误报恢复；可单独启用“持续无数据或查询失败也通知”，按健康异常等待时间产生独立事件 |
| 执行预览 | 只检查一次查询结果，不推进连续检测次数、不保存规则、不发送通知 |

例如设置每分钟检测、N=3、持续异常0秒：`异常 → 正常` 不告警，`异常 → 异常 → 异常` 在第三次检测时产生告警。恢复后再次异常，从头计算。

## 平台记录：通知限制不丢告警

正式触发即保存告警事件及各责任组响应，无论当前是日间、夜间还是静默。平台记录与实际发送是两回事。

- 夜间未通知的告警可在“告警响应”和“事件与发送记录”回看；夜间累计的每轮记录及达到门槛的动作保存在详情的“响应时间线”。
- 夜间已经恢复的告警保留触发与恢复记录，次日不重新拨号。仍异常的告警在日间窗口恢复后按日间策略通知。
- 规则待触发之前的每次检测不会单独生成完整评估历史；当前界面保存实例状态，正式事件保存触发、规则提醒及恢复等业务变化。
- 未发送的夜间记录不计入“实际通知人数”、成功发送轮数或接手率分母。

## 通知层：各级初始策略

下面是新告警组的初始模板，所有字段均可编辑。已有告警组保留其已保存的策略；可在各等级点击“使用初始策略”，核对后保存。

| 等级 | 日间 / 常规方式 | 夜间方式 | 初始时段 |
| --- | --- | --- | --- |
| P0 | 电话＋短信 | 同样使用电话＋短信，无夜间门槛 | 每天全天 |
| P1 | 电话＋短信 | 先仅记录，同一指标持续告警达到M轮后电话通知 | 日间每天09:00（含）～22:00（不含），其余为夜间 |
| P2 | 短信 | 仅记录，不通知 | 日间每天09:00（含）～22:00（不含） |
| P3 | 邮件＋Webhook | 仅记录，不通知 | 工作日09:00（含）～18:00（不含） |

时段按告警组时区计算，默认 `Asia/Shanghai`；可修改日间起止时间、通知星期。清空时段表示全天。P1夜间默认M=3、间隔5分钟、达到门槛后仅电话，也可选择短信或其他方式。P2初始策略关闭自动提级，避免夜间转为P1电话；如果显式开启提级，将按新等级重新检查通知策略。

夜间策略可选“仅记录，不通知”“直接通知”“累计持续告警后通知”，并可独立选择夜间渠道。

## 夜间M轮的明确口径

M是**已触发告警在平台上的持续告警轮数**，与规则层N次检测分别配置。

1. 规则正式触发后，夜间平台第一次确认该告警仍然异常，记第1轮。N次原始检测不会直接转成N轮通知。
2. 此后按告警组的“重复提醒间隔”确认同一指标仍然告警，每个间隔至多记1轮；不要求规则开启旧的重复提醒事件。
3. 达到第M轮才按夜间方式通知主班；备班、兜底的等待计时从这时开始。M=1表示第一轮即可通知。
4. 正常、查询失败、超过两倍检查间隔的检测中断会打断该指标的持续累计；不同实例、责任组和不同夜间窗口分别计数。
5. 静默时不累计；进程重启保留持久化记录，不把停机期间推算成已发生的轮次。需要新的规则检测结果才能推进下一轮。
6. 后台每秒扫描、多个人、多渠道、供应商失败和技术重试均不增加夜间轮数。
7. 已接手告警停止无人接手通知；正常恢复终止原事件，历史记录保留。

示例：规则每1分钟检测、N=3、持续异常0秒，P1夜间M=3、提醒间隔5分钟。00:00、00:01、00:02连续异常，00:02规则正式触发，平台记夜间第1轮；00:07仍异常记第2轮；00:12仍异常记第3轮并打电话。若00:09恢复，则保存整段记录，00:12和第二天都不会为这段已恢复事件拨号。

## 提醒、主备升级与接手

| 等级初始模板 | 重复提醒 | 通知备班 | 通知兜底 | 每层最多发送轮数 | 接手后处理期限 |
| --- | --- | --- | --- | --- | --- |
| P0 | 2分钟 | 5分钟 | 10分钟 | 6轮 | 30分钟 |
| P1 | 5分钟 | 10分钟 | 20分钟 | 6轮 | 60分钟 |
| P2 | 30分钟 | 关闭 | 关闭 | 6轮 | 120分钟 |
| P3 | 60分钟 | 关闭 | 关闭 | 1轮 | 关闭 |

- 通知星期外、仅记录的夜间、夜间门槛前及静默时暂停实际通知和升级的有效等待计时。
- 同组多主班可以并行通知；无人值班或没有可用联系方式时尝试下一层。组内任一有效成员接手即停止该组无人响应通知，不影响其他组。
- 每层达到发送上限后，可按配置继续等待备班/兜底升级；最终耗尽仍保留待接手状态及原因。
- 可选“无人接手提级”，在指定成功通知轮数并再等待完整提醒间隔后升到更高通知等级。原始告警等级保留；当前通知等级决定发送方式与窗口。
- 至少一个渠道被供应商受理才算一次成功发送轮次；平台夜间记录轮次、技术重试、多用户多渠道均不算额外成功发送轮次。
- 电话确认接听即接手；短信、邮件及普通群机器人通过授权接手链接接手。供应商受理不等于人工接手。
- 接手后处理期限到达且未续期，会重新通知备班；“仍在处理”可续期，也可转交。
- 恢复通知面向实际通知过的人及负责人，默认使用邮件、群消息、Webhook或推送，不再打电话或发短信；仅配置电话/短信的组不会发送恢复消息，但始终记录恢复事件。

## 三种间隔不能混用

| 设置 | 负责什么 |
| --- | --- |
| 规则“检查间隔” | 控制原始检测频率，推进规则层N次连续异常 |
| 告警组“重复提醒间隔” | 控制平台提醒轮次，推进夜间M轮；门槛打开后控制实际提醒 |
| 规则旧“重复提醒” | 控制持续异常的 `reminder` 业务事件；人员告警组由自己的响应策略驱动，不会因此多发一套通知，旧Webhook地址组仍用它 |
| 发送技术重试 | 处理连接失败、明确限流等；最多6次，指数退避，受供应商账号限流；不影响上述业务次数 |

短信/电话提交结果未知时不自动重发；已排队消息发送前重新检查事件、成员、联系方式、时段和渠道。已恢复、已接手、已取消的旧消息不会继续拨号。

## 配置入口

- 规则N次：告警中心 → 告警规则 → 编辑 → 连续异常检测次数；图表编辑 → 告警 → 检查与触发门槛。
- 夜间M轮：告警中心 → 告警组 → 成员、排班与策略 → 等级与升级策略 → 夜间策略、夜间持续告警轮数、夜间通知方式。
- 实际通知目标：系统设置维护供应商接入，用户资料维护手机号和邮箱，告警组选择接入与当班人员。

两个计数均为1～1000的独立整数。旧规则缺省N=1；旧组缺省夜间仅记录，编辑旧组不会自动开启夜间拨号。变更规则判定门槛会重新开始判定；开放事件应用新告警组策略需在详情点击“应用当前组配置”。
