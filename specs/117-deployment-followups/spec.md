# Feature Specification: 部署问题清单闭环

**Feature Branch**: `codex/117-deployment-followups`
**Created**: 2026-11-09
**Status**: Implemented and validated; [PR #160](https://github.com/workhold/lightmoni/pull/160) awaiting review
**Input**: 用户要求通过 MCP 读取《部署模块问题跟进》并解决其中问题。

## User Scenarios & Testing

### User Story 1 - 可信的遥测与资源展示 (Priority: P1)

管理员能从日志识别实际机器，从指标找到一致命名的数据表，从主机列表看到硬件容量并直接打开主机监控。系统内置监控在其所属资源或系统页面访问，用户大盘列表只展示自建大盘。

**Independent Test**: 直连中心的业务 SDK 上报机器名；真实 Agent 心跳上报核数和内存；各入口查询同一主机，用户大盘不混入内置项。
**Acceptance Scenarios**:
1. 未自定义机器名时日志包含运行机器名，显式名称覆盖默认值；指标表名采用中心的一致命名规则。
2. 主机展示 CPU 核数、内存总量及监控入口；无新心跳时显示未知，不显示伪造的零容量。
3. 应用、网站、主机、系统页面提供对应监控；不删除或覆盖用户大盘。

### User Story 2 - 日常管理与加载效率 (Priority: P1)

管理员能批量审阅并删除精确选中的容器，查看及修改支持的配置，清理未引用容器和镜像。镜像版本与大日志查询按需加载，过期结果不覆盖新查询。

**Independent Test**: 只删除选中的测试容器，保留未选对象和卷；大量标签和日志下请求数、并发和渲染范围有明确上限。
**Acceptance Scenarios**:
1. 容器清单及时展示最近观察，刷新有状态与时间；批量结果逐对象回读，失败可见。
2. 镜像使用仓库原生接口并限制清单读取并发，失效、超时及部分结果不能伪装成功。
3. 大盘编辑沿用现有 Grafana 交互和布局，日志使用已有虚拟滚动并通过大数据验收。

### User Story 3 - 配置与文件维护 (Priority: P1)

管理员在现有文件管理中创建文件或目录、编辑、重命名、删除和调整权限；配置编辑与浏览按类型高亮，失败保留输入。

**Independent Test**: 在可丢弃目录完成各动作并重新读取确认；并发修改、符号链接、根目录及无权限操作拒绝。
**Acceptance Scenarios**:
1. 文件和目录的修改绑定当前版本、当前 SSH 账户及明确目标，删除默认不递归清空目录。
2. 文件与 YAML 内容具有格式高亮和可读编辑区，中文、英文和窄屏均可操作。

### User Story 4 - 商店与已有编排 (Priority: P2)

管理员安装前可查看将使用的配置及官方/源码链接；应用图标可调整。已有 Compose 项目可经发现、审阅和确认纳入管理，明确展示不支持项目的原因，保留数据。

**Independent Test**: 查看商店配置，变更参数后预览更新；接管测试项目后原数据和准确项目身份保留，无第二份服务占用端口。
**Acceptance Scenarios**:
1. 已有图标编辑能力继续可用；商店显示真实可用的官方和源码地址，不编造链接。
2. 外部编排接管前说明重建影响、支持限制和数据位置，版本变化要求重新审阅。

### User Story 5 - 应用备份与部署迁移 (Priority: P2)

管理员可将应用多个容器的数据及配置作为一份备份下载，配置定时云存储备份并查看真实执行结果；能依照完整可验证步骤迁移 LightMoni 到新机器。

**Independent Test**: 多目录备份、校验、恢复后内容/权限一致；定时授权和吊销均生效；迁移预检、数据库一致快照、密钥/配置和遥测存储均纳入验收。
**Acceptance Scenarios**:
1. 明确记录备份包含的挂载和配置、不支持的数据及一致性要求，不能把单目录快照当完整应用备份。
2. 平台定时任务绑定真实管理员，在领取时复查权限与资源版本；平台持久凭据加密。离线云备份使用独立本机root持续授权和受保护运行时凭据，不把root计划冒充平台计划。
3. 整体迁移包含中心配置、主密钥、数据库、遥测存储及主机端地址衔接，不自动销毁原部署或覆盖目标。

### Edge Cases

离线、旧 Agent、权限撤销、并发修改、结果未知、超限数据、备份与源目录重叠、活动数据库、外部卷和目标非空均应明确报告，不自动重试未知写入或扩大删除范围。

## Requirements

### Functional Requirements

- **FR-001**: 按问题表第8—18行逐项核对最新主干，记录已有能力、剩余修改及实际证据，已解决行不重复实施。
- **FR-002**: 遥测默认机器身份和指标表命名一致，显式 SDK 配置仍优先。
- **FR-003**: 主机硬件信息来自实际心跳；系统监控在对应上下文访问，用户大盘不混入内置项。
- **FR-004**: 清单、日志和镜像版本的读取、并发和渲染均有上限，并避免串行逐标签查询瓶颈。
- **FR-005**: 文件与容器的写动作经人工审阅和精确版本核对，保留权限边界、审计、幂等与未知状态。
- **FR-006**: 安装配置可提前审阅，已有编排接管不得静默更改项目身份或数据位置。
- **FR-007**: 备份支持完整应用配置与多数据目录，定时云备份使用有效的持久授权。
- **FR-008**: 迁移工具与操作说明覆盖一致性、权限、回读和恢复原部署路径。
- **FR-009**: 架构变化同时更新仓库与 Doca 设计，保留原生图块并回读，记录同步证据。

### Key Entities

主机容量、遥测身份、用户大盘与内置监控、文件版本、容器选择、外部编排、应用备份、定时授权、迁移清单。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 全部11条待解决问题有当前实现判断、验收结果和剩余限制，无假报完成。
- **SC-002**: 文件/容器写入验收100%确认精确目标，未选对象、数据卷和其他文件保持不变。
- **SC-003**: 100个标签的读取可并行且不超过固定并发；2000行日志不同时渲染全部记录。
- **SC-004**: 备份恢复与迁移验收以实际内容和权限核对为准；失败和吊销路径拒绝继续写入。

## Assumptions

- 以最新 GitHub main 为基线；用户当前旧分支和未提交发行文件保留。
- 复用现有受管执行器、SSH/SFTP、备份与调度体系；不自动安装新权限或执行生产删除、恢复、迁移。
- 本次已有本地开发和可丢弃资源验收授权，生产发行和迁移需另有明确指令。
- 原文未规定新的指标前缀；先核对中心当前一致命名，避免臆造前缀或破坏现有查询。
