# SDD 167：助手内 Agent 更新审批

## 背景与实测

生产会话已证明 5 台主机只读 SSH 检查均可完成，但 5 个 `propose_agent_update` 并非同一错误：两台已有待审批/运行中/未知维护，两台使用已变化的发行摘要，一台有待执行/运行中/未知任务。用户无法从助手找到审批入口，只能看到失败和取消。需要在当前对话中提供与主机管理相同的原生审阅/确认路径，同时避免旧发行目录和盲目批量重试。

## 用户场景与验收

### US1：对话内审阅与确认

管理员成功创建 Agent 更新/回退计划后，在当前工具结果中直接看到完整计划、当前/目标发行、步骤、影响与有效期。

- 复用 `AgentUpdatePlanSummary` 和原生 `GET /machines/:id/agent-updates/:updateId`、`apply {confirm:true}`、`cancel`，不新增通用 apply/approve/execute 工具。
- 仅 `awaiting_approval` 且不属于 rollout 的计划允许确认；确认前必须重新读取当前计划并勾选已审阅。
- 取消计划使用独立二次确认，不能误触发执行。
- 仅管理员可见/使用审批动作；模型不能代替用户确认。

### US2：状态与错误保持真实

- apply 接受后展示执行中/核验状态及原记录链接，明确“已接受不等于升级成功”；只有原生 `succeeded` 才是成功。
- 状态已变化、过期、冲突或 API 失败时显示真实错误，不伪造审批或执行结果。
- 工具失败继续展示具体原因，不渲染审批按钮。

### US3：发行目录与批量行为

- 工具和系统指令要求每批更新前重新调用 `list_agent_releases`，按当前架构和不可变 SHA256 选择目标，不使用对话中的旧目录。
- 遇到“目标发行不可用或摘要已变化”时只允许刷新目录并重评一次；遇到已有维护或主机任务时不得盲目重试。
- `propose_agent_update` 在界面使用可读名称。

## 功能要求与成功标准

1. 计划摘要与审批动作严格依据工具返回的原生记录，校验 `id/machine_id/action/status/plan`；API 路径只能由记录 ID 编码生成。
2. 审批申请使用当前记录复核、`confirm:true`；取消与执行互斥，重复点击被禁止。
3. 解析、状态、过期和路径单元测试覆盖待审批、执行中、成功、失败、取消及非法记录。
4. 相关 Runtime、Web、Agent 更新回归、类型检查与构建通过；不实际升级生产主机。
5. 不改变原生计划、revision、owner、凭据复验、执行围栏、恢复或回滚语义。

## 架构影响

不适用。仅复用现有原生计划和审批 API 增加助手内展示与管理员交互，不改变组件职责、模型/工具权限、数据或控制路径、凭据边界、存储、协议或部署拓扑，因此不修改 `docs/system-design.md`。
