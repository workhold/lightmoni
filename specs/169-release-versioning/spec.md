# SDD 169：统一版本与本地镜像发布

## 背景

平台、Agent、MCP、SDK 和 Dockerfile 的版本号分散维护，当前均为 `0.1.0`。如果发布时只修改其中一处，会造成页面、Agent 安装包、MCP 元数据、SDK 文件名和镜像内容不一致。此次需要在发布主机页面优化版本前统一升级补丁版本，并形成后续 AI 可重复执行的检查流程。

## 用户场景与验收

### US1：发布前发现版本遗漏

- 根 `package.json` 是发布版本事实来源，本次从 `0.1.0` 升至 `0.1.1`。
- 一个命令检查平台、Agent、MCP、SDK、构建脚本、默认安装参数和 Compose 镜像标签是否一致。
- 一个命令完成后续补丁版本递增，避免 AI 逐文件漏改或误改第三方依赖版本。
- 每次推送前必须检查；只在发布 PR 中递增版本，不要求普通提交机械涨版。

### US2：镜像与发布版本可追溯

- 平台、Agent 和随镜像分发的 SDK 统一为 `0.1.1`。
- Compose 固定到 `v0.1.1-<UTC 时间>-amd64` 标签，镜像 OCI revision 记录实际构建源码 SHA。
- 本次只发布 Linux amd64 平台镜像，不使用 GitHub 流水线，不发布 arm64 镜像。
- 发布后验证镜像配置、中心健康检查、实例版本、MCP 版本及 Agent/SDK 发行文件名。

### US3：后续 AI 按 README 安全发布

- README 明确版本检查、递增、PR 合入、本地构建、验证和推送顺序。
- 凭据只通过受保护的 Docker 登录状态提供，不进入仓库、命令说明、日志或 PR。
- 未合入或未验证的代码不得发布；Compose 不使用会随时间漂移的 `latest` 作为固定发布标签。

## 功能要求与成功标准

1. 版本检查失败时列出具体不一致文件，递增操作幂等且不修改第三方依赖版本。
2. 构建、类型检查、版本一致性检查和必要的运行时回归通过。
3. 版本 PR 合入后才构建和推送镜像；最终 `main` 的 Compose 能拉取同一固定标签。
4. 不修改现有 API 行为、状态机、存储、协议或部署拓扑，不操作生产主机。

## 架构影响

不适用。本次只统一现有版本元数据、发行文件名和发布检查流程，不改变组件职责、数据或控制路径、凭据边界、存储、协议、部署拓扑及 AI/工具边界，因此不修改 `docs/system-design.md`。
