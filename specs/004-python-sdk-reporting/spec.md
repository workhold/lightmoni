# Feature Specification: Python SDK 远程上报控制

**Feature Branch**: `004-python-sdk-reporting`
**Created**: 2026-10-14
**Status**: Implemented and verified — [验收证据](verification.md)
**Input**: 用 SDD 开发 Python SDK 的远程停报、UID 排除和 QA/VIP 日志采样，与平台现有规则一致。

## User Scenarios & Testing

### User Story 1 - 保留重点日志，排除指定用户 (Priority: P1)
管理员为业务表设置 UID 排除、QA/VIP 全量、普通点击按比例保留。Python 服务无需重新部署即可执行规则。
**Why this priority**: 减少日志量，同时保留排查所需的重点数据。
**Independent Test**: 为同一表发送排除用户、QA、VIP、普通点击及未匹配日志，核对实际接收内容与保留原因。
**Acceptance Scenarios**:
1. Given UID 同时命中排除与 VIP, When 记录日志, Then 日志不上报，排除优先。
2. Given QA/VIP 与普通比例规则重叠, When 记录日志, Then 取最高保留比例。
3. Given 按 UID/会话采样, When 同一键产生多条日志, Then 稳定保留或忽略；键缺失时按单条事件选取。
4. Given 有表规则但日志没有命中, Then 忽略；未配置表规则时维持全量；空规则列表明确忽略该表全部业务日志。
5. Given 日志被排除或采样, When 同用户记录指标和链路, Then 指标和链路仍完整上报。

### User Story 2 - 远程暂停并恢复指定实例 (Priority: P1)
管理员按服务、实例、语言或资源属性停止监控上报，业务继续运行。删除规则后恢复新数据。
**Why this priority**: 避免异常实例持续产生无用数据，并允许无需改代码的运行控制。
**Independent Test**: 暂停有待发数据的实例，再恢复；检查所有信号和子表无停报期间的数据补传。
**Acceptance Scenarios**:
1. Given 命中停报规则, When 配置生效, Then 清空未提交的缓存和待发队列，停止日志、指标、链路及自监控。
2. Given 正在重试或等待发送结果, When 停报, Then 取消当前发送并阻止后续重试；已提交到接收端的数据不能撤回。
3. Given 停报前或期间创建的链路片段, When 恢复后结束, Then 不重新带回停报前或期间的数据。
4. Given 已停报, When 平台删除规则, Then 仍能取得配置并恢复新数据；本地暂停仍具有独立效力。

### User Story 3 - 配置故障时保持可解释的行为 (Priority: P2)
开发者可等待首次配置、查看生效版本和忽略计数；断网、非法配置或凭证失败不会覆盖最后有效规则。
**Why this priority**: 配置更新不能悄悄改变已生效的数据选择，也不能阻塞业务记录。
**Independent Test**: 有效配置后返回非法配置、认证失败及断网，核对规则不变和诊断可见。
**Acceptance Scenarios**:
1. Given 首次远程配置尚未成功, Then 沿用显式本地规则，未配置则全量；需要从首条数据执行规则时可显式等待。
2. Given 已有有效配置, When 新配置非法或不可达, Then 原子保留旧配置，记录脱敏错误，后续可恢复拉取。
3. Given 业务日志已冻结等待重试, When 仅日志策略变化, Then 不重新筛选或重写冻结正文和批次身份。
4. Given 关闭自监控但开启远程配置, Then 配置仍定期取得；关闭客户端后不再自动拉取。

### Edge Cases
- 布尔值、数字与字符串严格区分；同值整数和浮点数按数字匹配，长 UID 推荐字符串。
- 空规则、零比例、缺失采样键、非法字段、非有限数值、超大配置与重定向。
- 凭证轮换、并发更新、共享根生命周期的子表、旧 Span 结束及停报后迟到的发送结果。
- 受控忽略与容量/协议丢失分别统计，不能把主动采样解释为数据交付失败。

## Requirements
### Functional Requirements
- **FR-001**: 沿用平台现有规则，无需修改管理接口、认证、存储或其他语言规则；支持范围提示应包含 Python。
- **FR-002**: 排除优先；规则内条件全部满足，规则间取最高保留比例；支持有类型的相等集合和字段存在条件。
- **FR-003**: 支持稳定的用户/会话采样和缺失键时的事件采样，并与已有语言的选取结果一致。
- **FR-004**: 被保留日志记录保留比例、权重和规则名称；系统自监控日志不受业务日志采样影响。
- **FR-005**: 整体停报作用于全部信号和子客户端；清空缓冲、取消当前发送，恢复不补传停报期间的数据。
- **FR-006**: 配置持续更新独立于业务上报和自监控；更新失败保留最后有效快照，明确显示配置状态。
- **FR-007**: 支持显式刷新、本地规则更新和本地上报开关；远程表规则优先，本地或远程任意暂停均有效。
- **FR-008**: 不在业务记录路径访问网络；维持现有内存/批次限额、重试身份、上下文关联及退出边界。
- **FR-009**: 配置请求有时间和体积限制，不随重定向发送凭证，不把请求 Key、响应正文或 URL 放入诊断。
- **FR-010**: 有可执行的契约、真实 HTTP 生命周期和隔离中心/Agent 集成验证；证据明确区分真实存储与受控接收端。

### Key Entities
- **上报配置**: 生效版本、各表日志策略、实例停报规则。
- **日志策略**: 采样键、保留规则、排除规则；规则含条件及可选保留比例。
- **实例状态**: 本地/远程暂停状态、配置版本、忽略与失败计数。
- **冻结批次**: 已选取的数据、稳定身份和正文；日志策略变化不会改变它，整体停报可丢弃未确认批次。

## Success Criteria
- **SC-001**: 排除用户和未匹配日志实际接收数为零；配置为全量的 QA/VIP 日志全部接收。
- **SC-002**: 对固定的 10,000 个用户按 10% 保留，选取在 7%～13%，同一用户重复记录决策一致，跨语言固定向量一致。
- **SC-003**: 停报后全部信号不再发起新提交，恢复只接收新数据；受控等待响应/退避的发送在一秒内结束取消。
- **SC-004**: 非法/失败更新后原有效规则和版本不变，诊断可见；配置恢复后可在一个轮询周期加五秒内生效。
- **SC-005**: 仅日志策略更新不改变冻结重试的批次 ID、时间和正文，日志筛选不改变指标总量或链路内容。

## Assumptions
- 本次范围仅 Python 上报规则，不扩展其他语言、框架自动埋点或异步发送 API。
- 首次远程配置前沿用本地规则；需要从第一条记录生效的业务必须先等待显式刷新成功。
- 使用已有中心或 Agent 的上报认证；默认 30 秒更新配置。
- 已在网络中提交的数据无法撤回；SDK 缓冲仍只在内存中，fork 后需重新初始化。
- 保留比例表示选取概率，不是严格事件配额；错误日志要显式配置保留规则。
