# 实施计划

1. 保留并分类故障证据：旧维护器约 911 MiB RSS、现场约 956 MB、2 GB 无 swap 与低余量支持资源压力判断，但尚无内核 OOM 证据，不能声称唯一因果。
2. 维护器实现分阶段预算、磁盘/inode 准入、候选收尾、退出证据和验证后恢复；复用原 restore，不增加账户或执行框架。
3. 服务端修复 SSH probe 的整读残留，统一 observer 预算、明确 unknown 文案，增加固定恢复 bootstrap、修订和恢复审计。
4. 界面增加恢复影响确认、原事务恢复、凭据补录和 GET 超时退出；只读核对保持独立。
5. 本机隔离包测试和故障注入，必要时建立专用临时 Linux/systemd 环境。逐步验证实际资源约束，不在 vchive 重放旧高内存升级。
6. 更新 system-design/Doca 并回读；补验证证据，更新 PR95，不自行合入或以模拟冒充现场验收。
