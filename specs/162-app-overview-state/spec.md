# SDD 162：应用总览加载与状态核对

状态：规格先行；2026-11-14（Asia/Shanghai）；分支 `codex/162-app-overview-state`。

## 问题与目标

打开应用管理时，中心总览请求有时超过页面 10 秒自动刷新间隔。旧请求会被后一次轮询标记为过期，即使成功返回也不进入页面，首屏可能一直显示加载遮罩。已安装卡片又把保留服务地址、宽限、可用性保护和未知执行结果阻塞一概归为“待处理”，让管理员无法区分正在部署与需要核对的运行现场。

本轮使慢总览最终可见，减少同一总览请求的重复资源读取，并让应用卡片、详情、筛选和操作使用一致的状态证据。历史执行结果和服务实际健康仍以中心、Agent 和现有核对记录为准。

## 用户场景与功能要求

1. 管理员首次进入应用管理，`GET /ops/overview` 即使慢于 10 秒，也可在响应后看到卡片；定时轮询及窗口重新聚焦不抢占正在进行的读取。手动刷新及会触发新读取的主机/页面范围变化可以替换旧请求，旧响应不能覆盖新的范围或数据。纯本地筛选继续使用已有数据。请求失败应结束加载并展示既有错误与重试入口，不因自动刷新形成并行积压。
2. 中心总览在一次 HTTP 请求中仅读取一次资源集合，基于同一过滤结果计算 `total` 与前 1000 条 `resources`。除实例公开摘要增加可选 `unresolved_run_id` 外，现有鉴权、字段、排序、筛选、`limit`、`agents`、`machines`、`runs` 和 `capabilities` 响应语义不变。
3. 只按已启用且已发布的集群及其当前实例判断整体状态；禁用集群的遗留实例不影响启用集群。当前实例自身 `state=unknown` 或存在未人工核对的当前 unknown 执行记录时显示“结果未知”，包括保留 `running/healthy` 的日志作业未知结果；明确失败优先于“待核实”。否则 `availability=retained|grace|protected` 或 `recovery.state=blocked`、原因 `unknown_execution_result` 显示“待核实”。保留地址不证明健康。仅当每个启用目标的已发布修订应用完成、当前实例数及 `ready_instances` 均达到目标数且实例均有现有成功健康证据时才显示“运行中”；1/2 副本不能报运行中。零副本目标允许无实例或仅有已停/已移除实例；所有目标都为零时整体显示“已停止”，与其他就绪目标并存时不阻止整体运行。2→1 缩容要求目标槽位就绪、额外未退休实例已停或已移除；已退休旧副本不计入成功数量，也不触发本轮新增的应用动作门禁。未退休但已移除的实例若仍关联未核对当前执行，依旧触发写操作门禁。若没有启用的已发布集群，但禁用集群仍有非退休活动实例或实例摘要截断，则保守展示“待核实”，不宣称已停止；仅有已退休的遗留实例不阻止已停止判断。
4. 已保存的新资源修订与仍在运行的旧已发布修订分开标明，不把旧版本健康当成新配置已发布；若现有字段无法证明旧版本目标数量，保守地不报运行中。已安装卡片和详情共享状态投影；“待核实”在状态筛选中单列，不混入“待处理”或“失败 / 结果未知”，数量与可见卡片一致。中文、英文及状态颜色区分各态。
5. “待核实”和“结果未知”的卡片提供“核对状态”入口；启用集群显示运行中但任一非退休实例被未知执行阻塞时也提供该入口。点击后均打开现有应用安装记录抽屉，只读读取该应用资源与原执行记录，并优先展示当前未核对的 unknown 记录；有当前未核对记录时，已核对的旧 unknown 不抢占默认选择。历史列表只返回最近 100 条：若实例摘要的 `unresolved_run_id` 不在列表，抽屉通过既有 `GET /ops/runs/:id` 定向读取该原记录，再选择它；只有 `recovery=blocked/unknown_execution_result` 而无当前运行 ID 时，抽屉显示待核实并优先选择该应用历史中的 unknown 原记录。用户手动选择其他记录后，轮询不抢回选择。不新派发 `inspect`，以免撞上主机围栏。上述需要核对的卡片限制升级、停止、卸载和删除登记；未知执行阻塞（包括已禁用集群的非退休实例及 `unresolved_run_id`）也限制部署/重新部署。服务端对用户发起的 `deploy|stop|remove|reconcile` 在写入新的部署意图或实例期望状态前检查未核对执行并拒绝冲突动作，不能先保存新意图再发现主机围栏拒绝派发；服务自动恢复沿用原有机制。资源登记删除仍受既有 `store.remove` 对未核对历史运行的独立保护，已退休历史不绕过这一校验。记录抽屉在待核实/结果未知时禁用编辑、重新部署和快速安装重试。入口不得自动认定运行、改写 unknown 回执、释放主机围栏或重放受管任务。

## 验收标准

- 使用响应延迟超过 10 秒的真实页面与受控 API：首屏请求完成后显示应用，自动轮询和窗口焦点不产生与其重叠的总览读取；手动刷新和范围变化仍取得新数据，迟到旧响应不能覆盖。
- 总览接口的资源列表与总数来自同一集合，维持 1000 条上限及原排序；定向测试确认一次请求只调用一次 `store.list()`，接口形状和权限保持。
- 用受控资源分别验证新鲜健康、1/2 副本、0 副本已停止、2→1 缩容、`retained`、`grace`、`protected`、未知恢复阻塞、实例 `unknown`、运行健康但当前日志作业 unknown、明确失败与保护态并存、禁用集群遗留实例、已保存但未发布的新修订；卡片、详情、筛选计数一致。
- 所有显示“核对状态”的卡片点击后只打开应用原执行记录，不发送新 `inspect`；当前未核对记录落在最近 100 条列表之外时通过既有按 ID 读取端点定位，已核对的旧 unknown 不抢占当前运行或用户手选记录。卡片危险操作和抽屉中的编辑/重新部署/快装重试按上述门禁禁用。后端拒绝未知执行下用户发起的部署/停止/卸载/调和且不改变部署修订或实例期望状态。未知任务及其围栏保持原状，验收记录不把页面文案修正写成生产现场已恢复。
- 运行相关 Web、Runtime 类型检查、定向测试和构建；记录实际执行、跳过项与环境限制。

## 范围与兼容

不修改 Agent 队列补传、镜像仓库诊断、应用部署调度、健康判定来源、受管执行器、数据库结构或生产现场记录。`unverified` 仅为页面状态投影，不写入资源状态；实例公开摘要增加可选 `unresolved_run_id`，从既有当前运行记录及人工核对状态派生，不保存新状态。后端 `applied_revision` 对空实例集合使用 `every()` 可能产生真值；本轮前端用目标数、当前实例数和 `ready_instances` 阻止误报，后端计算修正另行跟踪。已有接口消费者及保存的应用记录无需迁移。本轮不自动发布或部署生产版本。

## 架构影响

适用：卡片“核对状态”的控制路径由提交新 `inspect` 作业改为打开既有应用安装记录抽屉，读取 `/ops/resources/:id` 与 `/ops/runs?resource_id=:id`；列表不含当前未核对记录时，通过既有 `/ops/runs/:id` 定向读取。中心从当前未核对运行记录派生公开 `unresolved_run_id`，并在部署意图写入前实施未知执行围栏；这是数据与控制路径调整。同步 `docs/system-design.md` 第 162 章与 Doca《LightMoni 系统设计基线》，保存后按最新版本回读目标章节和原生图节点、连线。没有新增存储、凭据边界或部署拓扑。
