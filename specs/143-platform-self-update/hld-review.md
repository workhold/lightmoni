## 一致性与安全审核

- **执行边界**：中心没有 Docker 控制权限；updater 独立持久执行，中心停止后仍能继续。
- **双写恢复**：已补充 SQLite → Spool 的同 ID 幂等投递和 updater 持久确认，避免崩溃产生两个执行任务。
- **切换幂等**：`switch_intent` 先持久化；切换命令结果不明时不盲目重放。
- **版本完整性**：页面审阅标签，执行固定 digest；标签漂移、来源修订或当前容器身份变化使旧计划失效。
- **时间语义**：上传、登记、首次发现分别保存；旧版本允许明确显示上传时间未记录。
- **成功证据**：Docker 实际镜像身份、中心健康和持久回执共同判定；HTTP 200 或命令返回 0 不足以证明成功。
- **数据边界**：不更新 ClickHouse/updater/Agent，不删除卷；不承诺数据迁移可回滚。
- **凭据边界**：发布、审批、拉取、Agent 和 SDK 身份分离；Spool 与事件不保存秘密。
- **权限事实**：updater 的 Docker 控制权限需要真实可写，不能沿用只读 socket 示例。
- **AI 边界**：MVP 不注册 AI 写工具，publisher 也无审批或执行权限。

## 自审后调整

1. 明确标准 Registry 读取是后续适配器，MVP 只承诺当前内部 Registry 的真实验收。
2. 增加 SQLite 与 Spool 崩溃一致性协议，规定领取前后的唯一写入方。
3. 明确中心不可用且拉取授权失效时保持中断，不绕过认证续跑。
4. 明确切换通过持久化目标状态文件完成，不直接修改仓库 Compose 文件。

## 后续 LLD 必须解决的问题

- updater 的打包方式、Spool 文件布局/权限和原子写实现。
- Compose 目标状态文件格式、配置摘要和固定命令参数。
- publisher 认证、时间格式/有效性和登记幂等错误码。
- 多架构 manifest 选择、本机 image ID 与 RepoDigest 的具体核验规则。
- updater 心跳、锁代次、恢复超时、事件上限和残留进程判定。
- 中心存储兼容元数据的发布来源与具体门禁。

这些属于设计细化，不需要改变当前 HLD 的组件职责；若评审改变部署拓扑、凭据或恢复边界，应先更新本 HLD。
