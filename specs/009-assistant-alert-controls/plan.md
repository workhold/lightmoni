# 设计

## 先业务能力，再 AI 适配

在 `domains/alert-capabilities.ts` 建立 AlertCapabilities，共享规则规范化、AST/来源表校验、版本检查、静默目标及权限判断、写入和副作用。现有 alert-api 路由委托该能力，不让助手复制 SQL 或循环调用自己的 HTTP。业务服务准备阶段异步校验，提交阶段同步复核版本并写入，可由调用方放入一个 SQLite 事务。

主服务先注册 Alerts 实例，再将共享能力注入 assistant。助手注册表提供有界读取工具与 `propose_alert_change`，不向模型注册应用工具。提案记录原业务对象、规范化后的候选对象、操作输入、目标版本、操作人、会话和 15 分钟期限。

## 确认与一致性

用户 GET 回读最新提案，在 Modal 中确认。独立 POST apply 重新执行共享准备校验，并在同步事务中复核提案和目标快照，提交业务副作用、读取最终对象、保存完成回执。相同 ID 重复 POST 返回原回执；输入不能覆盖存储的操作。保存回执失败回滚业务写入。权限按确认时的用户和告警责任关系重新判断。旧规则使用 revision；静默使用持久对象版本/指纹，防止旧记录和直接 API 更新绕过冲突检测。

模型收到有界的提案与 ID；后续对话把已持久化的实际提案状态回填至历史收据，并单独注入最近 20 条主服务状态，不受旧摘要/summary_through 遮蔽。可使用只读 get_alert_proposal 查询更早提案。工具成功代表提案已创建，不能表示业务变更已经应用。系统提示明确区分这两种状态。

## 前端

独立告警变更卡片（不复用代码审批 API）从服务回读，展示前后值、影响、状态及有效期。确认前再回读，显式 Modal 确认才发 POST。提交后刷新告警页数据；上下文包含当前页签/筛选/规则标识，不含凭据或身份授权。

## 兼容与交付

不增加运行时依赖，不改既有页面权限模型。提案表新增不改历史会话格式；旧静默记录继续读取。新增 GET 单项与 PUT 静默接口为业务复用提供稳定入口。规格与可复跑验证记录随功能 PR 交付，Agent 部署设计作为相邻独立文档交付。
