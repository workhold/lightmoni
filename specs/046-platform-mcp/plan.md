# 实施计划

本轮为设计交付；下列运行时代码阶段均未完成。详细 HLD/LLD 见 [平台 MCP 架构](../../docs/platform-mcp.md)。

## 阶段 A：共用能力层

- 新建 `runtime/src/capabilities/` 的描述符、Principal、Dispatcher、策略、审计与结果投影。
- 将助手会话绑定的提案迁到通用提案服务，保留原 owner、会话与审计；来源会话变成关联信息。
- Web、现有助手工具改为薄适配器，继续调用原领域服务；先验证相同输入、主体和资源得到相同权限与行为。
- 建统一执行索引及领域事件/outbox 事务，不复制现有队列、租约或回退逻辑。

## 阶段 B：MCP 与客户端授权

- 采用官方 MCP SDK 的受支持 Streamable HTTP 实现，固定并测试协议版本；入口仅绑定已配置外部 origin，不接受 Host 头生成授权地址。
- 协议适配隔离：候选 2025-11-25 兼容实现使用初始化握手；2026-07-28 使用 server/discover/每请求元数据，独立验收后再声明支持，不能混用已移除的会话或握手。
- 增加独立个人令牌、授权管理界面、安全工具目录、结构化错误与有界结果。
- 实现 OAuth 2.1 授权码、PKCE S256、资源/授权服务器发现、授权同意、刷新轮换与撤销；复用平台登录会话完成用户身份验证，不复用第三方登录模块充当授权服务器。
- 先采用预注册客户端，明确 redirect URI 规则。自动客户端注册或 Client ID Metadata Documents 另做 SSRF 与配额治理，不无界抓取客户端 URL。
- 首期工具仅安全读取和提案；在平台 Web 审批。至少用固定版本的本地 Codex 和 Claude 客户端完成真实握手、发现、读取、提案、平台确认和结果查询。
- 支持仅 Bearer 配置的客户端可先进行试验验收；OAuth 及两类真实客户端未验收前，不宣称通用开箱即用。

## 阶段 C：受控自动化与自定义能力

- 引入独立服务主体、scope/资源授权、配额及授权管理员撤销/降权后的调度处理。
- 参数化任务模板与能力注册表，支持 Node.js/POSIX shell 与结构化内置动作；模板代码、解释器、参数 schema 与上限固定版本。
- 固定模板/目标/参数/时间/次数的持续授权；主机操作提交时和执行前重验。高影响操作仍需人工审阅。
- 对外稳定 HTTP 自动化接口复用 Dispatcher；不要求普通程序模拟 MCP，不建立第二套权限。

## 实施验收门

1. 传输：初始化/协商、JSON 响应、POST/GET/DELETE、非法 Origin、版本、大小/超时/并发上限；不支持的能力不广告。
2. 授权：PKCE、精确 redirect/resource/audience、过期/撤销、刷新重放、降权、scope 和目标交集、对象 ID 越权；跨客户端和跨用户会话隔离。
3. 工具：发现过滤不是唯一鉴权；直接调用、resources/read、分页游标、源码读取、查询和输出字段均不能绕过授权。主机范围令牌不能通过任意 SQL 访问全库。
4. 执行：UI/内置 AI/MCP 得到相同提案和审批条件；幂等重试不重复派发、同键不同内容冲突、断连后查询原执行、撤销后待执行重验、unknown 不自动重跑、取消不得伪造已停止。
5. 回归：现有告警/静默、任务、服务发布、运维与生命周期状态机保持语义；迁移前历史提案的 owner/审批约束不得放宽。
6. 客户端：记录 Codex/Claude 实际版本、授权方式、tools/list、tools/call、提案链接和真实执行回执，不以 curl 成功代替客户端互操作。
7. 文档：仓库与 Doca 同 PR 同步，图用原生块，回读验证文本、节点、边。
