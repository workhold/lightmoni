## 背景

LightMoni 的系统设计同时维护在仓库和 Doca。只修改其中一处会让后续 Codex 开发者看到互相矛盾的组件边界、数据流或安全规则，尤其容易把规划中的架构误认为当前实现。项目需要一条所有开发者都能执行、审查和追溯的同步门。

## 目标

1. 让所有 Codex/开发者在判断架构影响后，明确更新仓库设计和 Doca 在线副本。
2. 让原生流程图等 Doca 内容保留可编辑性，并通过回读证明保存结果。
3. 让 PR 审查者能从描述和 SDD 找到同步章节、链接和证据。
4. 允许纯 UI、文案或局部实现改动声明“不适用”，避免无意义改图。

## 架构变更判定

以下任一变化都算架构变更：组件职责或生命周期；数据/控制路径；凭据签发、边界或用途；存储与一致性；HTTP/OTLP 等协议；部署拓扑、服务发现或升级；AI、Agent、SSH 与工具权限边界。仅改变局部样式、错误文案、测试或不改变边界的内部重构，可在 SDD/PR 中说明不适用理由。

## 强制流程

1. 在 spec、plan、tasks 和 validation 中写明架构影响判断以及仓库/Doca 两端的目标章节。
2. 先从最新主干同步并完成代码与 `docs/system-design.md` 的修改；若有原生图，保留无关块、稳定 ID、节点和连线语义。
3. 使用受保护的 Doca MCP 凭据写入对应在线章节或图块，不把 token 写入文件、参数、日志、URL、PR 或文档正文。
4. 用最新 `seq`/`epochId` 回读文本和图块，核对保存内容、节点与边；将成功回执和限制写入 `validation.md`。
5. PR 描述必须列出：架构影响（是/否）、仓库设计章节、Doca 链接、Doca 写入与回读结果，或不适用理由。
6. Doca 不可访问、鉴权失败、冲突未解决或保存未确认时，工作项保持未完成并如实报告。

## 验收标准

- `AGENTS.md`、constitution 和总设计都能指向同一条双端同步规则。
- 架构变更的 SDD 明确列出两端章节和回读证据；非架构变更有不适用理由。
- 本次规则已写入仓库 `docs/system-design.md` 和 Doca 在线文档，且回读内容与规则一致。
- PR 描述包含同步记录；仓库搜索和提交差异不包含凭据。
