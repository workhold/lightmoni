# 手动部署仅由人工改变服务成员

**Created**: 2026-11-06
**Branch**: `codex/098-manual-service-membership`
**Status**: Implemented and verified

## 用户要求与问题

手动部署只有人工才能改变。当前已发布的单实例 OpenResty 在心跳或健康观察过期后会撤下服务端点，并删除入口 A/AAAA 和网站 CNAME；配置对账还会自动重新部署手动应用。最低在线比例只属于托管调度，不能用提高比例替代手动模式的人工控制。

## 场景与验收

1. 手动应用曾成功就绪，随后 Agent 离线、检查失败、容器意外停止/缺失、作业失败或结果未知：持续显示真实异常，保留已确认的服务成员、端口和地址，不因健康变化删 DNS、不迁移、不自动重新部署。覆盖单/多实例、超过 60 分钟及中心控制器重建。
2. 手动 OpenResty 和手动业务后端用于网站时，同样保留入口 A/AAAA、网站 CNAME 及反代上游；观察失败不得冒充配置发布撤销。从未成功就绪的实例不能进入发现或 DNS。
3. 人工确认的停止、卸载、部署位置修改、网站停用或 DNS/路由配置修改仍按已授权目标执行和回读；配置草稿本身不能撤销已发布成员。
4. 发现手动配置漂移时，对账只运行 inspect 并报告需要人工处理；人工重新部署后可以恢复正常。已撤销 Agent 或主机身份变化仍遵守身份边界，不能借保留地址恢复旧身份。
5. 托管模式保留已有默认 5 分钟宽限、60% 向上取整、先就绪后切换与显式停止语义。

## 行为契约

- `serving` 表示已授权发布的成员，`healthy`/`ready_instances` 表示当前确认健康；二者独立。
- 手动实例的历史成功由持久 `last_ready_at` 证明；`serving` 被旧健康逻辑清零时可据此恢复，前提是当前身份绑定有效、未退役且期望运行。没有成功证据不能复活。
- 手动异常保留成员显示 `availability=retained`；不会承诺自动替换。`min_available_percent` 不控制手动成员。
- 手动部署漂移返回 `manual_deployment_action_required`，不调用 apply/stop/remove 修复。
- 手动网关重载失败/未知时，网站当前回执保留错误，另在现有状态 JSON 保存最后成功发布证据；DNS 只保留该证据与当前人工发布配置的交集，不发布未成功的新域名。人工已授权的离线停止可在原机器恢复后完成，未知执行不可自动重放。
- 对已人工发布的网站/证书/托管后端变化，网关仍执行原有授权配置传播；这不授予按手动应用健康变化重建容器的权限。
