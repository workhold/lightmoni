# 中心配置权威与手动服务成员保留

**Created**: 2026-11-06
**Branch**: `codex/098-manual-service-membership`
**Status**: Implemented and verified

## 用户要求

两种部署模式都以中心已发布配置为权威，机器实际状态不一致时自动强制恢复符合中心配置。手动模式仅固定中心指定的部署位置、成员和服务解析，机器异常不能反向改变中心期望；托管模式允许中心根据故障反馈执行迁移，按期望副本补齐，并遵守最低可用预算。

## 场景与验收

1. 手动应用成功就绪后，Agent 离线、检查失败、容器意外停止/缺失：保留中心已发布成员、端口、反代上游和 DNS，报告真实异常。在线时自动在中心指定原机器恢复配置/容器，不迁移到其他机器，不改写中心规格、修订、期望状态或部署数量。覆盖单/多实例、两小时离线及控制器重建。
2. 两种模式的配置对账均通过 inspect 比较实际内容；明确不一致或已知失败按当前中心配置 apply/stop/remove；容器配置明确不一致时首次修复即强制重建，不能仅重复 compose up，回读确认后恢复 in_sync。人工新发布使旧 inspect 证据失效；未知执行先核对，身份、权限和执行互斥不绕过。
3. 手动网关和业务后端失败保留入口 A/AAAA、网站 CNAME 及反代上游；失败重载保留最后成功发布依据，未验证的新域名不发布。从未就绪的实例不能发布。
4. 人工确认的停止、卸载、位置、网站路由和 DNS 变更仍按中心新目标收敛；已撤销身份、退役或人工期望停止的实例不复活。
5. 托管应用期望3副本、60%最低比例时最低保留2；机器失联超出默认5分钟宽限后由中心启动替换，当前配置成功就绪后切换；有可用容量时补齐3个当前实例，不用修改副本目标适配机器故障。原旧进程按路由确认与排空流程清理。

## 状态与兼容

serving 是中心已发布成员，healthy/ready_instances 是当前确认健康，二者独立。手动已就绪成员依持久 last_ready_at 保留或恢复，异常标记 availability=retained，表示等待中心配置恢复，不表示需要人工重新批准原配置；最低比例不用于手动自动撤流。网站失败回执在既有状态 JSON 保存简短 published 成功证据，当前错误继续显示。未接入深度对账能力的旧 Agent 继续明确要求升级，不伪造内容一致。

## 架构影响

适用：服务成员、发现/DNS路径及中心配置对账边界；更新 docs/system-design.md 第93章。没有新增权限、表、端点或 Agent 协议。原生图保持；既有在线段落同步记录随最终契约修正并回读，不扩展新的在线维护范围。
