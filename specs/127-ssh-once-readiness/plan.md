# Implementation Plan: SSH 单次命令发行就绪判断

**Branch**: `codex/127-ssh-production-qa` | **Date**: 2026-11-12 | **Spec**: [spec.md](spec.md)

## 现状与根因

中心以 SSH 凭据和已有 helper 能力心跳推断受管执行已就绪，未证明远端发行包支持单次入口。旧版也上报 `operations.managed.v1`，故可生成计划，之后固定 SSH 命令才因缺少入口失败。普通作业和手动脚本有同类准入空隙。

## 设计

1. 定义三个受控单次入口能力名。普通 Agent 心跳声明 `jobs-once`；签名 helper 心跳声明 `managed-once`、`task-once`。中心严格验证声明集合，缺失视为不支持。现有心跳 JSON 存储和身份认证不变，未增加凭据或任意命令执行能力。
2. 保留已在线验证的 `16b151337cc94c1b7f3f7de56bdcad561759c85b` 为精确迁移例外。只认可完整 `source_revision` 和 `state_schema=1`；后续构建通过显式声明，不能按 SHA、版本号的字典顺序推断。
3. 签名 helper 受管能力状态与计划审批检查 `managed-once`；手动脚本在排队前检查 `task-once`；普通 Agent 作业在排队前检查 `jobs-once`。定时脚本不需要 `task-once`，保留原循环与身份门禁。
4. 中心扫描旧队列时再查对应证据；无证据的未领取记录写明确升级失败码，不建立 SSH 连接。已领取与 unknown 继续原租约和核对。缓存的旧心跳可证明发行兼容性，但不能替代 SSH 凭据、主机密钥、身份绑定和签名授权。
5. 页面将升级原因显示为可读的中英文提示。测试覆盖旧发行、精确迁移发行、新字段、Agent 离线、定时任务和旧队列。

## 实施顺序

先完成规格、设计、契约、任务，再修改心跳生产者和中心验证，接入各准入点，补聚焦测试、类型检查与验收记录。架构同步与原生图块回读在同一 PR 中完成。

## 架构与兼容

Agent/helper 到中心的心跳协议增加可选单次能力字段；旧版保持可接入并继续上报/定时任务，但不能新建无法执行的中心主动操作。中心部署先于机器升级时，精确迁移发行保持可用。没有新增存储列，原历史记录不迁移。仓库与 Doca 的系统设计同步后回读。
