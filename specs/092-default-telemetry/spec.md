# Feature Specification: 应用默认监控与持续上报恢复

**Feature Branch**: `codex/092-telemetry-recovery`
**Created**: 2026-11-04
**Status**: Draft
**Input**: 用户反馈 SDK、Agent 均无可见上报；要求每个应用默认采集容器指标和日志、网站 QPS/access log，以及 SDK 打点和日志采集。

## User Scenarios & Testing

### User Story 1 - 应用默认容器监控 (Priority: P1)

管理员部署应用后，直接打开该应用的监控与日志即可查看其所有容器的负载和输出，无需另配采集任务。

**Why this priority**: 运行成功但看不到运行质量，无法排障。
**Independent Test**: 部署会持续输出日志的多容器应用，检查各容器负载和两种输出流。

**Acceptance Scenarios**:
1. **Given** 已运行的应用，**When** 等待两个采集周期，**Then** 各运行容器出现 CPU、内存、网络、磁盘及进程指标，并可按实例过滤。
2. **Given** 容器产生 stdout/stderr，**When** 查看应用日志，**Then** 能看到对应内容、容器和部署身份，重试不丢失已接受日志。
3. **Given** 采集不可用或上报失败，**When** 查看监控，**Then** 显示具体阶段和原因，不能以健康或空图代替故障说明。

### User Story 2 - 网站流量与访问日志 (Priority: P1)

管理员发布网站并产生请求后，可从网站查看 QPS、状态和耗时及访问日志。

**Why this priority**: 域名可访问不能证明流量正常。
**Independent Test**: 对两站点分别发送带标记请求，核对网站流量和日志互不混入。

**Acceptance Scenarios**:
1. **Given** 已发布网站，**When** 请求该域名，**Then** 2分钟内出现该站的访问日志和每秒请求量。
2. **Given** 手动后端或托管服务绑定，**When** 打开网站流量，**Then** 两类绑定均可查看该网站的数据。
3. **Given** 相同入口承载多个网站，**When** 按网站过滤，**Then** 仅显示目标网站日志。

### User Story 3 - SDK 指标与日志可见 (Priority: P1)

已接入 SDK 的应用用平台默认身份持续上报后，管理员可在监控和日志中发现、筛选数据。

**Why this priority**: 一次验收日志入库不能代表业务持续上报可用。
**Independent Test**: 实际 SDK 连续产生计数、测量、分布和日志，并从用户页面查询。

**Acceptance Scenarios**:
1. **Given** 使用默认配置初始化的 SDK，**When** 产生指标和日志，**Then** 数据带应用/实例身份送达且页面可查，无需写死中心地址或密钥。
2. **Given** SDK 使用自选逻辑表，**When** 查看该应用监控，**Then** 可发现该应用已上报的指标与日志，并保留容器采集入口。
3. **Given** 应用未接入 SDK 或未产生新数据，**When** 查看 SDK 区域，**Then** 明确显示缺少上报，不伪造业务打点。

### Edge Cases

- 旧 Agent 和中心版本不一致；采集主进程存活而辅助采集故障。
- 单个容器日志失败、超长日志、队列满及网络中断，不能静默阻断其他容器指标。
- 停止、重建、退役的实例保留历史身份；多容器不串数据。
- 没有流量或业务日志时，区分零请求、无新日志、采集异常。
- 保留现有鉴权、凭据和存储，不暴露 Docker socket 给普通 Agent 或 SDK。

## Requirements

### Functional Requirements

- **FR-001**: 每个已部署应用默认采集对应容器指标及 stdout/stderr，涵盖系统应用。
- **FR-002**: 容器数据具备应用、集群、机器、部署、容器身份；范围由中心校验。
- **FR-003**: 网站默认提供站点范围的访问日志、QPS、状态及耗时；手动后端和托管绑定均可查看。
- **FR-004**: SDK 指标和日志可通过应用身份发现和查询，涵盖用户自选逻辑表。
- **FR-005**: 主机 Agent 持续采集并上报主机指标，页面能判断最新数据时间与故障。
- **FR-006**: 采集、排队、发送和查询故障必须可见；一个信号失败不能无提示地吞掉其他已产生信号。
- **FR-007**: 既有数据与游标保留，重试采用既有持久队列和身份鉴权，不绕过权限模型。
- **FR-008**: 验收必须同时包含真实持续上报、存储回读和用户页面结果；模拟数据不能替代线上证据。

### Key Entities

- 应用/实例/容器：业务与默认采集归属。
- 网站：站点身份与请求流量范围。
- 采集状态：最近尝试、成功、错误及队列状况。
- SDK 信号：具备应用身份的业务指标和日志。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 线上每个运行应用在2分钟内出现新容器指标；会输出日志的容器在2分钟内可查该日志。
- **SC-002**: 各网站测试请求在2分钟内对应到各自访问日志和非零QPS。
- **SC-003**: SDK 至少跨3个周期的指标与日志可在页面看到，应用与实例归属正确。
- **SC-004**: 采集失败的验收场景能看到原因；日志采集失败时新指标仍能成功入库。
- **SC-005**: 连续3次现场复查有新采样，历史数据、凭据与原业务保持可用。

## Assumptions

- 默认容器采集与业务 SDK 分开；SDK业务打点需要应用实际调用SDK，不能自动制造业务事件。
- 沿用现有保留策略、鉴权和发布流程；本轮不引入新采集组件或第三方监控系统。
- 线上部署和真实复测沿用当前任务已授权的发版测试范围；PR合并仍须用户授权。
