# Feature Specification: 生产运维恢复与可读上报

**Feature Branch**: `codex/097-production-operations`
**Created**: 2026-11-06
**Status**: Validated; implementation in progress
**Input**: 用户要求全部变更经 PR 合入 main，发布 Docker/GitHub，通过 1Panel 更新中心，逐项实测部署/卸载/日志/告警/大盘及 Agent 安装、卸载、升级；只操作 zz-bj-1；SDK/Agent 上报应包含机器名和服务名，不能只显示难读的机器 ID。

## User Scenarios & Testing

### User Story 1 - 维护和部署能完成 (Priority: P1)
管理员在巡检开启时仍能完成 Agent 升级、卸载重装和应用部署、停止、启动、升级、卸载。
**Why this priority**: 当前自动巡检占用队列导致维护难以开始，阻断恢复。
**Independent Test**: zz-bj-1 开启巡检，完整执行一次维护和应用生命周期，并核对实际状态、数据保留。
**Acceptance Scenarios**:
1. 只有后台只读巡检排队时，用户维护能取得窗口；运行中写操作和未核对未知结果保持真实阻塞。
2. 部署资源不足或端口冲突时显示真实失败原因；调整后可恢复，停止/卸载不被无关历史错误永久阻止。
3. 卸载重装后身份与平台一致，业务数据及受控保留的数据目录不丢失。

### User Story 2 - 遥测持续到达且可读 (Priority: P1)
用户在主机、容器、网站、业务 SDK 的指标和日志中看到机器名和服务名。
**Why this priority**: 无数据和难读身份会妨碍排障。
**Independent Test**: zz-bj-1 产生容器与业务活动，三轮查询新数据并核对可读来源。
**Acceptance Scenarios**:
1. 中心已登记主机名时，Agent 上报包含该机器名及服务名，归属仍绑定正确主机和应用。
2. 业务 SDK 由平台注入名称后，日志和大盘可读；名称变更和离线补传不会改写旧批次身份。
3. 旧 Agent 或缺失名称时有明确降级，伪造名称不能改变授权归属。

### User Story 3 - 全流程验收可核对 (Priority: P2)
管理员依据真实回执核对应用、主机、日志/指标/SDK、网站/证书、告警和大盘。
**Why this priority**: 页面可打开不足以证明数据和操作正常。
**Independent Test**: 矩阵逐项记录入口、触发、回执、实际结果和恢复动作。
**Acceptance Scenarios**:
1. 告警完成触发和恢复，大盘可保存、读取并显示真实新数据。
2. 所有生产机器操作仅用 zz-bj-1，vchive 保持原状态，未完成项明确记录原因。

### Edge Cases
- 巡检与维护竞争、重启、SSH 失联、未知执行、重复点击。
- 卸载保留数据、身份变化、证书依赖、资源和端口不足。
- 中文或同名主机、空服务名、已删除业务补传、旧 Agent、队列重试。
- SDK 伪造归属、查询空窗口、通知不可达。

## Requirements

### Functional Requirements
- **FR-001**: 后台只读巡检不得无限饿死维护，真实活动写操作和未知结果仍保持阻塞。
- **FR-002**: Agent 安装、升级、卸载、重装须有持久回执和实际身份核验，保留业务数据。
- **FR-003**: 应用部署、停止、启动、升级、卸载反映机器真实结果和明确失败原因。
- **FR-004**: Agent/SDK 上报与展示含机器名、服务名；稳定 ID 保留归属和去重用途。
- **FR-005**: 主机、容器、网站和业务日志/指标持续可查，告警和大盘由真实数据验证。
- **FR-006**: 所有机器操作仅限 zz-bj-1，不改写未知历史，不绕过现有权限/凭据边界。
- **FR-007**: 新发现先记规格、设计、契约和任务，再修复、回归、PR 合入、重发与复测。
- **FR-008**: 控制路径或上报契约变化在同一 PR 更新仓库设计；按用户最新要求只维护本地设计，不再同步 Doca。
- **FR-009**: 管理员可从独立的“修正 Agent 状态”入口恢复被旧任务或未知维护永久阻塞的主机；入口不受这些旧状态禁用。经固定 SSH 目标两次只读核实程序、服务、helper、工作进程及操作锁均已不存在后，审阅影响清单并填写原因，取消旧身份排队任务、审计结束未知执行和维护、撤销旧身份并恢复重新接入能力。不能将未知操作改写为成功；原状态与结论持久保留，业务容器、配置和数据不删除。远端仍在执行或身份不符时明确拒绝并显示原因。

### Key Entities
- 维护窗口：主机、请求类型、等待原因、执行和恢复结果。
- 遥测身份：稳定归属、可读机器名/服务名、来源及时间。
- 验收项：入口、对象、触发、回执、实际结果、证据、恢复及未完成原因。

## Success Criteria

### Measurable Outcomes
- **SC-001**: 仅后台巡检时维护两分钟内开始，活动写操作和未知结果不会被覆盖或重放。
- **SC-002**: zz-bj-1 的 Agent 升级/卸载重装、应用部署/停止/启动/升级/卸载各完成至少一次且核对结果。
- **SC-003**: 至少三轮连续观测得到新主机/容器/SDK 数据和日志，可读来源与实际对象一致。
- **SC-004**: 告警一次触发及恢复，大盘一次保存/读取/真实数据展示；未完成项有具体原因。
- **SC-005**: 线上版本与发布摘要一致，产品改动经 PR 合入 main，验收矩阵没有未经证明的通过。

## Assumptions
- 使用已有登录、SSH 凭据和正常维护机制；用户已授权合并、发行、部署和验收。
- 名称帮助理解，ID 维持绑定；卸载测试保留已有业务卷和历史数据。
- 未获明确收件方授权不向外部发测试通知。
- GitHub 大 Agent 附件上传超时，完整包已经随 Docker/中心下载服务发布；该限制不算线上验收通过。

## 完整管理安装兼容性补充

zz-bj-1 为 CentOS 8/glibc 2.28，旧 libcap-ng 对当前内核 CAP_LAST=40 的 setpriv `-all` 明确返回 127，导致 helper 安装降权核验失败并回滚。普通任务仍须 UID/GID 为专用非 root 账户、附加组为空、NoNewPrivs=1，五个能力集合全部为零。兼容修复只能使用实际内核支持的完整能力编号集，不得省略能力清除、改用 root 或回退到不完整配置。无效/超出支持范围的内核信息应拒绝。

## 内存导出器与中心运行指标

线上大盘的中心运行指标为空，本地复现 RuntimeMonitor 使用的无 HTTP Key 自定义导出器将 lightmoni 批次静默出队（delivered=0、pending=0）。自定义回调已经是调用方明确配置的传输，不应由默认 HTTP Key 门禁丢弃。恢复该内存路径，同时默认 HTTP 无 Key 的系统批次保持不发送，匿名 SDK 不生成自身诊断，禁用上报仍生效；HTTP 服务端系统表鉴权保持。

## 重装后应用绑定恢复

恢复后真实对账发现 DBX apply 成功但 inspect 反复 configuration_matches=false，导致持续重建。实际 manifest 命名卷 source=dbx-data，Docker 按固定 Compose 项目生成 lm-<instance>_dbx-data；巡检直接比较逻辑名产生误报。巡检须按 Compose 的项目范围、显式 name 和 external 规则解析实际卷名，再核对目标、读写权限及卷身份；实际错误卷或配置漂移仍必须判失败。停止期望须保持停止，修复后原测试实例恢复运行并验证不再重复重建。

生产计划 7543443f71664643d219620309b3e883 的实际回执发现：Gitea 已期望移除、从未就绪、无容器，但失败安装遗留固定目录且无 state.json，阻止其余四个实例恢复。对中心明确期望 removed 且核验无容器的旧记录，允许审阅后仅退役中心记录，完整保留原目录；界面须明确“退役已移除记录，保留原目录”，不能当作已恢复运行或已核实受管数据。期望运行的实例继续要求完整受管状态；复验新增容器或期望变化必须拒绝。

新版重装 f44bf6f4da78aea21e005ec0a181109e 成功后，OpenResty 正常部署仍停在 agent_reinstall_stateful_review_required；旧容器和数据保留，但没有完成核对的入口。管理员需要主机级计划，逐一审阅旧实例、当前身份、容器归属和固定数据位置，再复验同一证据后转移中心绑定。此操作只修正绑定，不执行 Docker 写操作，不改变部署位置、期望副本、端口、数据目录或服务配置；后续正常对账恢复中心配置。旧 Agent 仍在线、未审计未知执行、路径或标签不安全、已有数据却缺受管状态、目标或配置变化都拒绝。

## 私有镜像巡检与 Gitea 安装补充

Gitea 当前停止回执 succeeded，但 status.last_error 仍为 2026-11-05 的 insufficient_node_capacity，导致成功停止后页面显示失败。新部署/停止/移除请求被正常接受后，清除资源级旧启动错误及对应集群旧错误/等待提示；真实新失败继续保留，历史执行不删除，未知状态不改成成功。

ABC 只读实际核对发现 manifest.command=[]，Docker Cmd=[node,server.mjs]；镜像、资源、环境及端口一致。单容器表单的空 command/entrypoint 应继承镜像默认值，归一化时省略空列表，避免成功启动后被误报并持续重建。非空覆盖仍逐项核对；Compose 显式空列表语义保持。

生产 ABC Demo 的只读深度巡检连续被 approval_invalid: private_registry_cache_policy_changed 取消。相同缓存策略经全局对账规范化 JSON 后字段顺序改变，不得被误判为策略变化；比较必须遵守 JSON 值语义，真实端点、来源、模式、版本、上游许可或额外字段变化仍拒绝。修复不得跳过缓存授权或扩大 Agent 权限。

Gitea 新安装默认宿主 SSH 端口为 2222→22，克隆地址 SSH_PORT 与固定映射一致，允许显式配置其他固定端口。前后端均以配方声明的宿主端口为默认值；已有资源不静默改写。线上按实际集群预算选址，完成 ABC 验收后释放其测试容器配额，再验证 Gitea 实际部署与健康。

卸载后的空容器巡检是正常收敛：中心期望 removed 且成功证明无容器时应保持 removed，不能变成 stopped 或累加健康失败；期望 stopped 的成功停止观测同样不累计运行健康失败。若仍存在停止容器，不能声称已移除；运行期望下无容器继续视为故障。
# Website access ownership

生产验收发现网关域名分组的内部片段 ID 被写入 website_id，中心按真实网站登记校验后降级为无网站归属的容器日志。网关必须分别保留片段 ID 与原网站 ID：目录、证书和路由命名继续使用片段 ID；访问日志使用原网站 ID。中心继续核实当前网站登记、集群与 OpenResty 归属，不采用任意日志声明，也不改写历史日志。
