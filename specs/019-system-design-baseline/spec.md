## 背景

LightMoni 已经形成中心服务、Web 工作台、业务 SDK、独立 LightMoni Agent、AI 助手、主机 SSH 引导和告警响应等多个能力域。现有 `docs/architecture.md`、`docs/contracts.md` 和各编号 SDD 分别描述了其中一部分，读者需要在多个文件之间拼接系统边界、数据流、凭据和部署规则。这样容易把历史方案误读为当前实现，也容易让后续功能绕过公共契约。

本 SDD 建立一个完整的系统设计入口，覆盖 HLD、LLD、驱动目标、设计原则、状态机、接口、安全边界、部署、验收和演进路线。它不取代各特性 SDD 的详细契约；特性 SDD 负责变更级别的需求、计划和验证，本文件负责说明这些特性如何联动成为一个系统。

## 目标

1. 为产品、开发、运维和 AI 助手提供一个可从上到下阅读的系统设计基线。
2. 明确中心、Agent、SDK、Web、AI、ClickHouse、SQLite 和外部通知之间的责任边界。
3. 固化 SDK 直连中心与 SDK 经 Agent 两种模式，说明两者何时使用、凭据如何隔离以及不自动切换的原因。
4. 固化 Agent 的一等运行节点定位：它独立于业务进程生命周期，承担采集、拨测、日志、任务分发、队列和节点身份；它不是业务 SDK 的强制代理。
5. 把 AI 助手的只读分析、人工确认变更、SSH 首次引导和未来 Agent 工具能力放进同一安全模型。
6. 让 README 有一个稳定、明显且唯一的完整设计入口。
7. 为后续 SDD 提供统一的事实来源、验收门和变更评审标准。

## 非目标

- 本变更不新增业务运行时代码、数据库迁移或 API 行为。
- 本变更不把规划中的 Agent Executor、远程任意命令、节点端模型调用或多租户写成已实现能力。
- 本变更不重新定义各特性 SDD 已经批准的字段；冲突时必须开新的 SDD 修订公共契约。
- 本变更不自动合并任何功能分支。

## 设计要求

- 任何新模块先写 spec、plan、tasks、validation，再实现代码。
- 总设计必须区分“当前实现”“兼容路径”“目标架构”和“未验收边界”。
- 凭据和用户数据不得进入日志、URL、模型消息、浏览器响应或诊断导出。
- 公共协议、存储列、认证和错误语义由中心契约统一维护，不能由页面或 Agent 自行发明。
- 每个端到端能力必须能沿数据流找到接收、持久化、查询、错误处理和验收证据。

## 覆盖范围

| 能力域 | 设计覆盖 | 事实来源 |
| --- | --- | --- |
| 中心服务 | HTTP、认证、模块装配、SQLite、ClickHouse、后台任务 | `runtime/src/server`、`docs/contracts.md` |
| Web 工作台 | 路由、权限、主题、国际化、数据和 AI 交互 | `web/src`、SDD 016 |
| 业务 SDK | record、日志、Trace、窗口聚合、重试、两种上报模式 | `sdk/*`、SDD 010/011/012 |
| LightMoni Agent | 独立运行、采集、拨测、文件日志、队列、心跳、控制和数据凭据 | `runtime/src/agent`、SDD 006/010 |
| AI 助手 | Mastra worker、工具、Pi coding agent、审批、用量和模型管理 | `runtime/src/assistant`、`ai-runtime`、SDD 001/005/008/009/013 |
| 主机接入 | SSH 凭据、预检、部署计划、交互终端、Agent 接管 | SDD 014/017/018 |
| 告警 | 规则、静默、值班、通知、响应和 AI 提案 | `runtime/src/domains`、`docs/alert-response.md` |
| 交付运维 | Compose、Agent 包、升级、备份、健康检查和验证 | `compose.yaml`、`docs/agent-deployment.md` |

## 完成标准

- `docs/system-design.md` 完整描述 HLD 与 LLD，并链接到已有详细文档和 SDD。
- `README.md` 在开头指向总设计，且不再承担另一套相互矛盾的系统定义。
- SDD 目录包含 spec、plan、tasks、validation 四类文件。
- 所有新增内部链接存在；文档中明确标出 SDK 发布矩阵与代码实现可能不同步的地方。
- 能通过文档审查回答：数据从哪里来、由谁认证、写到哪里、如何重试、谁可以改变它、失败后如何恢复。
